## 1. 기획 배경

### 1.1 요구사항 원문

1. 긴급대체 후보는 **법규와 내규를 전부 충족하는 인원만** 추출한다.
2. 내규는 병동(group)마다 자기 설정값이 다르므로 **그룹 설정 전체**를 반영한다.
3. **솔버 디폴트 세팅**도 판정 근거에 포함한다.
4. 점수는 **소프트**로 매기되, 법규·내규 자체는 **하드 게이트**로 건다.
5. 한 명만 교체하는 **1인 스왑이 최선**의 구조다.
6. 1인 스왑이 불가능하면 **같은 날 여러 명을 움직이는 연쇄 수정안**을 제시한다.
7. 연쇄로 생기는 변경 내역도 **정상적으로 표시**하고 **사용자 선택으로 적용**까지 되어야 한다.

### 1.2 기존 구현의 한계

`app/services/replacement_recommend_service.py` (118KB) 를 조사한 결과:

| 위치 | 현재 동작 | 문제 |
|---|---|---|
| `_rule_safety_score` (:591) | 규칙 위반을 `risk +=` 로 **감점만** 함 | 하드락 위반 후보가 점수만 깎인 채 **추천 목록에 남는다**. 요구사항 1 위배 |
| `_evaluate_single_slot` (:1900) | 하드 배제는 비규제 조건(중복배정 등)만 | 연속근무·나이트회복 같은 규칙은 배제 사유가 아니었다 |
| `_recommend_bulk_markov` (:2554) | 이름과 달리 **greedy 순차 3-path**. 백트래킹 없음 | 마르코프도 아니고 연쇄 탐색도 아니다 |

즉 "전부 충족하는 인원만"이라는 요구를 만족하는 경로가 없었다.

> 이 표는 **코드를 읽고** 내린 판단이다. 실제로 그런지는 §5.8 에서 데이터로 확인했다 —
> 기존 추천 1순위 후보의 **86.7%**, 전체 후보의 **89.0%** 가 솔버 하드 규칙 위반이었다.

### 1.3 접근 방식 선정 과정

문제의 형식 명칭은 **NRRP(Nurse Rerostering Problem)** 이고, 목적함수는 **MPP(Minimum Perturbation Problem)** — 원본 근무표에서의 변경량 최소화다. 후보 접근을 순서대로 실측했다.

**후보 1 — 전체 재생성**: 결원자만 빼고 근무표를 다시 만든다.
→ 20.3s. 게다가 근무표 전체가 뒤집혀 MPP 목적에 정면으로 반한다. 탈락.

**후보 2 — LNS(Large Neighborhood Search) + CP-SAT**: 결원 주변 셀만 자유변수로 두고 나머지를 고정한 뒤 재최적화. `_run_cp_sat_basic` 을 스크립트에서만 몽키패치해 고정셀을 주입하고 측정했다.

| 자유 범위 | 전체 시간 | solve 구간 | 고정비 | 변경 셀 |
|---|---|---|---|---|
| x±1일 ~ x±4일 | 약 6s | 2.1s | **4.4s** | 18–92셀 |
| y축만 (K=0, 당일 1열) | 6.52s | 2.1s | **4.4s** | **3셀** |

핵심 관찰: **고정비 4.4초가 자유변수를 줄여도 전혀 줄지 않는다.** 파이프라인 오버헤드(데이터 로드, 전처리, 모델 빌드)라 문제 크기와 무관하다. 자유변수를 1열까지 좁혀도 6.5초 → **즉답 경로로는 못 쓴다.**

> 단 이것이 LNS 폐기를 뜻하지는 않는다. 뒤에서 y축이 못 푸는 구간(나이트 결원)이
> 드러나고, 그 구간에 한해 LNS 를 후속 경로로 재도입해 품질을 실측한다(§5.6·5.7).

**후보 3 — y축 독립 검사 (채택)**:

y축만 열면 문제가 *"이 한 칸을 누가 채울 수 있나"* 로 좁혀진다. 이때 각 후보의 판정은 **다른 후보와 독립**이다(같은 칸에 동시에 들어가지 않으므로). 독립이면 조합 최적화가 필요 없고, 후보별 규칙 검사를 순회하면 끝난다. CP-SAT 없이 순수 함수 호출만으로 풀린다.

→ 실측 후보당 약 0.03ms. 고정비 4.4초가 통째로 사라진다.

## 2. 수학적 정식화

> 표기는 마크다운 뷰어 어디서나 읽히도록 평문으로 쓴다.
> `|X|` 는 집합 X 의 크기, `1[조건]` 은 조건이 참이면 1 아니면 0.

### 2.1 기호

| 기호 | 의미 |
|---|---|
| `N` | 간호사 집합. 크기 `n` |
| `D` | 해당 월 일자 집합. 크기 `d` |
| `S` | 근무코드 집합 (D, E, N, MID, O, 각종 휴가코드 …) |
| `x0` | **원본 근무표** — 이미 확정된 것. `n x d` 표 |
| `x` | 제안 근무표 |
| `main(s)` | 근무코드 `s` 의 대표 근무형 (`shifts.default_shift`) |
| `A(x, day, t)` | `day` 일에 `t` 근무로 배정된 간호사 집합 = `{ v : main(x[v][day]) = t }` |
| `R[t]` | `t` 근무 요구 인원 (`day_req` / `eve_req` / `nig_req`) |
| `H` | 하드 제약 집합 — **솔버가 `m.Add` 로 강제하는 것** (§3) |
| `SOFT` | 소프트 제약 집합 — 솔버가 슬랙으로 최소화하는 것 (§3) |
| `V(x)` | `x` 가 위반하는 **하드** 제약 인스턴스 집합 |
| `W(x)` | `x` 가 위반하는 **소프트** 제약 인스턴스 집합 (배제하지 않고 감점) |

### 2.2 문제 정의

결원 이벤트 `e = (v*, day*, s*)` — 간호사 `v*` 가 `day*` 일의 `s*` 근무를 수행 불가.

```
목적:   최소화  delta(x, x0) = SUM(v in N) SUM(day in D) 1[ x[v][day] != x0[v][day] ]

제약:   (1)  x[v*][day*] = OFF                 ← 결원 처리(주어진 조건)
        (2)  V(x) \ V(x0) = 공집합             ← 원본 대비 하드 위반 증가 없음
```

**제약 (2)의 형태가 핵심이다.** `V(x) = 공집합`(절대 무위반)이 아니라
`V(x) \ V(x0) = 공집합`(**원본 대비 악화 없음**)이다.

원본 근무표가 이미 깨뜨리고 있는 항목까지 제안 탓으로 돌리면 그 날짜의 모든 안이
자동 탈락한다. 실측 근거는 §5.3 — 절대 기준이면 해결불가 75.3%, 원본 대비면 24.6% 다.

### 2.3 y축 제한 — 문제를 한 열로 좁힌다

자유변수를 결원일 `day*` 한 열로 한정한다.

```
고정:   x[v][day] = x0[v][day]        (모든 day != day*)
```

이때 목적함수가 한 열의 합으로 축소된다.

```
delta(x, x0) = SUM(v in N) 1[ x[v][day*] != x0[v][day*] ]
```

탐색 공간: `|S|^(n x d)` → `|S|^n`.
중환자실1 기준 `35명 x 31일 = 1,085셀` 에서 **35셀**로 줄어든다.

이 축소가 핵심이다. 한 열만 열면 후보끼리 상호작용이 없어 조합 최적화가 필요 없고,
후보별 독립 검사로 풀린다.

### 2.4 이동과 연쇄 (ejection chain)

**이동(move)** 하나는 셀 한 칸의 변경이다.

```
m = (v, day*, s_from -> s_to)
```

**제안(proposal)** 은 이동의 순열이며, 연쇄 조건을 만족한다.

```
P = < m1, m2, ..., mk >

s_to(m1)      = s*                    ← 결원이 비운 자리를 m1 이 메운다
s_to(m[i+1])  = s_from(m[i])          ← m[i] 가 떠나며 비운 자리를 m[i+1] 이 메운다
                                        (1 <= i < k)
```

즉 `v*` 가 비운 `s*` 를 `m1` 이 메우고, `m1` 이 떠나며 생긴 빈자리를 `m2` 가 메우는
식으로 이어진다. 조합 최적화 문헌의 **ejection chain / cyclic transfer** 이웃 구조와
같은 형태다.

**종료 조건** — 마지막 이동 `mk` 가 둘 중 하나를 만족하면 연쇄가 닫힌다.

```
(a)  s_from(mk) 가 근무가 아님                     ← 휴무자가 들어와 빈자리가 안 생김

(b)  |A(x, day*, main(s_from(mk)))| - 1 >= R[main(s_from(mk))]
                                                   ← 떠나도 인원이 요구치를 충족
```

`k = 1` 이면 **1인 스왑**, `k >= 2` 면 **k인 연쇄**다.

### 2.5 커버리지 제약

```
|A(x, day*, t)| >= R[t]        (t = D, E, N)
```

이 식이 §2.4 의 종료 조건을 만든다. 후보가 근무 중이면 그를 데려올 때 원래 근무의
인원이 1 줄므로, 여유가 없으면 연쇄를 한 단계 더 진행해야 한다.

### 2.6 등급 최소인원 (누적 의미)

등급은 **1이 최상위**이고 요구는 **누적**으로 해석한다.
`constraints_json` 의 요구 `(근무 t, 등급 g, 인원 m)` 에 대해:

```
| { v in A(x, day*, t) : grade(v) <= g } | >= m
```

즉 "grade g 이상 m 명"이 아니라 **"grade g 까지 누적 m 명"** 이다.

인원이 0인 등급의 요구는 인원이 있는 상위 등급(번호가 큰 쪽)으로 **cascade** 한다.

```
casc(g) = g                                    , pop(g) > 0 이면
        = min{ e : e > g, pop(e) > 0 }         , 아니면
```

`pop(g)` 는 그 병동에서 등급이 `g` 인 간호사 수다.
등급 3이 한 명도 없는 병동에서 "등급 3 요구 2명"을 그대로 검사하면 영원히 미달이므로,
실제로 존재하는 상위 등급으로 요구를 옮긴다.

### 2.7 소프트 점수

하드로 거른 뒤 **남은 안들의 우선순위만** 정한다.

```
cost(P) = 2.0 * (k - 1)                    ← 연쇄가 길수록 불리
        + SUM(i = 1..k) w(m[i])            ← 이동별 비용
        + 4.0 * |W(x) \ W(x0)|             ← 소프트 제약 신규 위반

w(m)    = 3.0   , s_from(m) 이 근무가 아닐 때   ← 휴무 소실
        = 1.0   , 근무일 때                     ← 근무형 변경
        + 1.5   , main(s_to(m)) = N 이면        ← 나이트 추가 부담
```

정렬 키는 `(k, cost(P))` 오름차순 — **인원 수가 먼저, 그 다음이 점수**다.
MPP 목적(변경량 `delta` 최소화)을 사전식(lexicographic)으로 우선한다.

가중치의 대소 관계만 의미가 있다. 절대값은 조정 가능한 정책값이며
`replacement_chain_service.py` 상단 상수(`W_CHAIN_STEP` 등)로 노출돼 있다.

### 2.8 복잡도

| 단계 | 복잡도 | 설명 |
|---|---|---|
| 1단계 스윕 | `O(n * r)` | `r` = 후보 1인당 규칙 평가 비용 |
| 깊이 k 연쇄 | 최악 `O(n^k)` | 실제로는 커버리지 여유 조건이 대부분의 가지를 즉시 닫아 가지치기가 강하다 |

실측 (`n = 35`, `k <= 3`): 케이스당 중앙 27.2ms, p95 47.5ms, 최대 61.3ms.
최악 `O(n^3) = 42,875` 가 아니라 실제 평가 수백 회 수준에서 끝난다.

## 3. 하드/소프트 분류 — 기준은 솔버 구현

### 3.1 판정 기준

**솔버에서 하드로 계산되면 긴급대체에서도 하드, 솔버에서 소프트면 소프트.**
법규냐 내규냐를 사람이 판단해 나누는 게 아니다. 근무표를 만든 주체가 솔버이므로,
대체 판정이 솔버와 다르면 "생성은 되는데 대체는 안 되는" 모순이 생긴다.

라이브 경로는 `fallback_lex.py` 하나다(`SKIP_PRIMARY` 기본값 `"1"` 이라 primary 는 죽은 코드).
`build_model()` 안에서 다음으로 판별한다:

| 코드 형태 | 분류 |
|---|---|
| `m.Add(expr)` 로 직접 강제 | **하드** |
| 슬랙 변수를 만들어 `safety[...]` 에 담고 2단계에서 Minimize | **소프트** |

### 3.2 결정적 발견 — `safety` 딕셔너리의 절반이 죽어 있다

`fallback_lex.py:1456-1475` 의 `safety` 딕셔너리는 "안전/법규 위반(정량 슬랙)"이라는 주석과 함께
17개 키를 선언한다. 주석만 보면 전환·연속근무·회복이 전부 소프트로 보인다.

해당 규칙은 별도로 `m.Add` 하드로 강제된다.

### 4.2 솔버 디폴트 정합

`get_roster_config` 는 DB row 를 그대로 준다. 값이 없으면 `None` 인데, 솔버는 `NurseRosterConfig` dataclass 디폴트로 동작한다. 이 차이를 안 맞추면 대체추천이 솔버와 **다른 판정**을 낸다.

```python
_ALIAS = {"max_conseq_work":   "max_consecutive_work_days",
          "max_nig_per_month": "max_night_shifts_per_month",
          "two_offs_per_week": "enforce_two_offs_per_week"}

def effective_config(raw):
    """DB 값이 비면 솔버 dataclass 디폴트로 채운다."""
    d = NurseRosterConfig()
    out = dict(raw or {})
    for k, a in _ALIAS.items():
        if out.get(k) is None:
            out[k] = getattr(d, a, None)
    for k in ("not_one_night", "nod_noe", "banned_day_after_eve",
              "two_offs_after_two_nig", "two_offs_after_three_nig",
              "sequential_offs", "max_conseq_off"):
        if out.get(k) is None:
            out[k] = getattr(d, k, None)
    if out.get("three_seq_nig") is None:                    # bool 토글 ↔ 수치 상한
        out["three_seq_nig"] = getattr(d, "max_consecutive_nights", 3) >= 3
    return out
```

### 4.3 3단 구조

```
1) 스윕(sweep)     빈 칸 하나를 메울 후보를 전 요건 하드 검사로 추림
                   → (즉시가능, 연쇄필요) 로 분류
2) 연쇄(chain)     연쇄필요 후보를 데려오면 그 자리가 비므로 1)을 재귀 적용
3) 재검증(verify)  만들어진 제안을 '결과 상태' 기준으로 통째로 다시 검사
```

3)이 따로 필요한 이유: 1)은 이동 하나씩 보는 **증분 검사**라서 이동들이 서로 간섭하는 경우를 놓친다. 실제로 재검증 단계가 증분 검사를 통과한 제안 중 5건을 등급 미달로 잡아냈다(§5.2).

### 4.4 핵심 코드

**스윕** — 후보 분류:

```python
def sweep(dd, shift, state, c, exclude):
    """(dd, shift) 를 메울 후보 → (즉시가능, 연쇄필요)."""
    main = c.main_of.get(shift, shift)
    assign = day_assign(state, c, dd)
    ok, need_chain = [], []
    for cid in state:
        if cid in exclude:
            continue
        cur = next((s for d2, s in state[cid] if d2 == dd), None)
        if cur is None:
            continue
        cur_main = c.main_of.get(cur, cur)
        if cur_main == main:
            continue          # 이미 그 근무 — 옮겨도 결원이 안 메워진다
        ns = move(state, c, cid, dd, shift)
        # 원본에서 이미 위반 중인 항목까지 후보 탓으로 돌리지 않는다. 새로 생긴 것만 본다.
        before = set(personal_violations(cid, dd, cur, state, c, assign))
        if set(personal_violations(cid, dd, shift, ns, c, assign)) - before:
            continue
        if cur in c.cats["work"]:
            have, need = len(assign[cur_main]), c.req.get(cur_main, 0)
            if need and have - 1 < need:
                need_chain.append((cid, cur, cur_main))   # 빈자리가 생긴다 → 연쇄
                continue
        ok.append((cid, cur))
    return ok, need_chain
```

**연쇄** — 같은 스윕의 재귀 적용:

```python
def find_chains(dd, shift, state, c, depth, used, path, out):
    if len(out) >= RAW_LIMIT or depth > MAX_DEPTH:
        return
    ok, need_chain = sweep(dd, shift, state, c, used)
    for cid, cur in ok:                       # 여기서 연쇄 종료
        out.append(path + [(cid, dd, cur, shift)])
        if len(out) >= RAW_LIMIT:
            return
    for cid, cur, _m in need_chain:           # 한 단계 더 들어간다
        find_chains(dd, cur, move(state, c, cid, dd, shift), c, depth + 1,
                    used | {cid}, path + [(cid, dd, cur, shift)], out)
```

**재검증** — 원본 대비 악화 판정:

```python
def verify(moves, base_state, c, origin_state):
    """결과 상태로 다시 검사하되, 판정은 '원본 대비 악화 금지'다."""
    st = base_state
    for cid, dd, _cur, new in moves:
        st = move(st, c, cid, dd, new)
    dd  = moves[0][1]
    who = {m[0] for m in moves}
    before = state_issues(origin_state, c, dd, who)
    after  = state_issues(st,           c, dd, who)
    return sorted(after - before)             # 새로 생긴 위반만
```

**신규 규칙 1** — 순수 OFF 4연속 금지:

```python
def four_off_violations(seq, c):
    """순수 O 4연속 금지 — fallback_lex.py:917 `is_pure_o x4 <= 3` 하드.

    `enforce_4o_hard` 는 DB 에 값이 없으면 솔버 디폴트 True 라 대개 활성이다.
    휴가/공가는 '순수 O' 가 아니므로(:639 is_pure_o) OFF 코드만 센다.
    """
    if not bool(c.cfg.get("enforce_4o_hard", True)):
        return []
    return [f"순수 OFF {length}연속(4연속 금지)"
            for _s, length in _runs(seq, {c.off_code}) if length >= 4]
```

**신규 규칙 2** — 나이트 회복 (하드락 4·5):

```python
def night_recovery_violations(seq, cats, cfg):
    """3N 후 OFF 2회 / 2N 후 OFF 2회. 기존 검사기에 없어 새로 만든 유일한 규칙."""
    out = []
    n2, n3 = bool(cfg.get("two_offs_after_two_nig")), bool(cfg.get("two_offs_after_three_nig"))
    if not (n2 or n3):
        return out
    for start, length in _runs(seq, cats["night"]):
        if length not in (2, 3) or (length == 2 and not n2) or (length == 3 and not n3):
            continue
        end = start + length - 1
        for k in (1, 2):                       # 직후 2일이 모두 비근무여야 한다
            j = end + k
            if j >= len(seq) or (seq[j][0] - seq[j - 1][0]).days != 1:
                break
            if seq[j][1] in cats["work"]:
                out.append(f"{length}N 직후 OFF {k}일째 아님")
                break
    return out
```

### 4.5 적용(쓰기) 경로

`POST /replacement/recommend` (`app/routers/roster.py:2683`) 는 읽기 전용이고, 근무표 셀을 쓰는 기존 경로는 **`POST /save`** (`app/routers/roster.py:1653`) 다. 이 엔드포인트는 그리드 전체를 받아 `ScheduleEntry` 를 통째로 교체한다.

따라서 **적용을 위한 새 쓰기 엔드포인트가 필요 없다**:

```
추천 API  → 제안 목록(moves) 반환      (읽기 전용, 지금 구조 그대로)
프론트    → 사용자가 안 선택
프론트    → 선택한 moves 를 그리드에 반영
프론트    → POST /save 로 기존 저장 경로 사용
```

백엔드 작업 범위는 **추천 응답에 `moves` 배열(연쇄 제안)을 추가**하는 것으로 끝난다.

`:1608` 에서 먼저 return 하므로 구조상 SINGLE 에만 붙는다. 의도한 결과다.
BULK 는 여러 날을 한꺼번에 비우므로 슬롯을 독립 평가하면 커버리지 계산이 틀린다.

**적용 경로는 그대로** — `ChainProposal.moves` 를 프론트가 그리드에 반영하고
기존 `POST /save` 로 저장한다. 새 쓰기 엔드포인트를 만들지 않았다.

### 4.7 발견 — 대체추천과 생성기가 서로 다른 config 를 읽고 있다

구현 중 실 DB 검증에서 드러났다.

| 경로 | config 출처 |
|---|---|
| 근무표 생성 (`_fetch_latest_config`, `roster_create_service.py:415`) | 요청 `config_id`, 없으면 **그룹 최신** config |
| 기존 대체추천 (`replacement_recommend_service.py:1429`) | **`schedule.config_id`** |

중환자실1에서 이 둘이 실제로 갈렸다:

| config | `max_conseq_work` |
|---|---|
| `schedule.config_id = 1618` | **1** (연속근무 1일) |
| 그룹 최신 `1631` | 5 |

`schedule.config_id` 로 판정하면 원본 근무표가 대량 위반 상태가 된다(하드 위반 6건 → **187건**).
델타 판정에서는 그만큼 면책 범위가 넓어져 **연속근무 제약이 사실상 무력화**되고,
해결 가능 건수가 부풀려진다(1인 스왑 445 → 495).

신규 모듈은 **그룹 최신 config** 를 쓴다 — 생성기와 같은 출처여야
"생성은 되는데 대체는 안 되는" 모순이 안 생기기 때문이다.
기존 `replacement_recommend_service` 의 config 출처는 이번 변경 범위 밖이라 두었다(§7.2 에 등록).

### 4.8 LNS 2단 배선 블로커 — **§10 에서 해결됨**

> **이 절은 당시의 판단 기록이다.** 결론은 안 A(생성 파이프라인 dry-run seam)로 정해져
> §10 에서 구현·검증을 마쳤다. 아래 블로커 분석은 왜 A 를 골랐는지의 근거로 남긴다.

당시 §5.6 에서 LNS 품질을 확인했다고 봤지만(그 측정은 §10.2 에서 무효로 판명됐다),
코드로는 반영하지 못한 상태였다. 붙이려면 넘어야 할 구조적 문제가 있었다.

**실측 하네스가 쓴 방법은 프로덕션에 못 쓴다**

| 하네스 | 왜 프로덕션 불가 |
|---|---|
| `_run_cp_sat_basic` 몽키패치로 고정셀 주입 | 런타임 패치는 서비스 코드에 둘 수 없다 |
| 생성된 schedule 을 사후 DELETE | 추천 한 번에 근무표를 만들었다 지우는 건 부작용이 크다 |

**`generate_roster_service` 를 그대로 부를 수 없는 이유**

| 지점 | 하는 일 |
|---|---|
| `roster_create_service.py:4467` | `request_schedule_service` 호출 → **Schedule 행 생성 + commit** |
| `:6324` | `_persist_entries` → **ScheduleEntry 저장** |
| `:6449` | `send_assignment_roster_created_push` → **간호사에게 푸시 발송** |

추천 하나 만들자고 실제 근무표를 만들고 **간호사들에게 알림까지 쏘게 된다.**

**중간에서 끊는 것도 답이 아니다**

`_run_cp_sat_basic` 은 한 번만 불리지 않는다 — `:5585`(본 호출) 외에
`:5677`(재시도), `:5809`, `:5906`, `:5988`, `:6015`, `:6174`, `:6404`(완화·보정 경로)까지
**8곳**에서 호출된다. 첫 호출 직후 반환하면 프로덕션보다 품질이 나쁜 해를 내놓게 된다.
seam 은 `_persist_entries`(`:6324`) 직전이어야 하는데, 그때는 이미 Schedule 행이 만들어져 있다.

**따라서 남은 선택지는 셋이다** (§7.2 에 등록)

| 안 | 내용 | 부작용 |
|---|---|---|
| A | `generate_roster_service` 에 `dry_run` 파라미터 — Schedule 행 생성과 `_persist_entries`·푸시를 모두 건너뛰고 `generated` 그리드만 반환 | 2,000줄 함수에 분기 추가. 생성 파이프라인은 시스템에서 가장 민감한 영역 |
| B | 비동기 — SQS 워커에 넘기고 결과만 회수 | **A 보다 크다.** 워커도 결국 같은 `generate_roster_service` 를 부르므로 A 의 문제가 그대로 남고, 거기에 비동기 인프라·폴링 UI 가 더해진다. B 는 A 를 해결하는 게 아니라 **포함**한다 |
| C | 1단(y축)만 배포하고 LNS 는 별도 과제로 분리 | **0.** 코드를 안 건드린다. 대신 N 결원 63% 는 당분간 수동 처리 |
| D | CP-SAT 없이 y축을 2일 블록으로 확장 | **폐기.** 실측 결과 4.8% 밖에 못 푼다(§5.7) |

**A 도 깔끔하지 않다** — `generate_roster_service` 안에 `db.commit()` 이
`:4409`, `:4441`, `:5562`, `:5761` 네 곳 있어 **트랜잭션 롤백으로 되돌릴 수 없다.**
Schedule 행은 `:4467` 의 `request_schedule_service` 가 만들고,
그 뒤 2,000줄이 `schedule.schedule_id` 를 참조한다.
dry-run seam 을 제대로 내려면 그 참조들을 임시 객체로 흘려보내야 한다 —
**긴급대체 기능에 묻어서 할 일이 아니라 그 자체로 독립된 리팩터링 과제다.**

### 5.4 실험 3 — 해결불가 183건의 원인

근무별로 갈라 보면 결과가 한쪽으로 완전히 쏠린다:

| 근무 | 해결 | 불가 | 불가율 |
|---|---|---|---|
| D | 240 | 8 | 3.2% |
| E | 238 | 10 | 4.0% |
| **N** | 83 | **165** | **66.5%** |

해결불가 케이스에서 후보들이 차단된 사유 (총 6,222회 평가):

```
 1155회  이미 N 근무 중
  961회  단일 나이트          ← 하드락 7
  726회  연속 나이트 4일       ← 하드락 3
  171회  3N 직후 OFF 2일째 아님 ← 하드락 4
   72회  금지전환 N→D          ← 하드락 2
   72회  금지전환 N→E          ← 하드락 2
   ...
```

**구조적 해석**: N 결원을 당일 1칸만 바꿔서 메우려면 —
- OFF인 사람을 넣으면 → 그게 **1N**이 되어 하드락 7 위반
- 이미 N 근무 중인 사람은 → 옮겨도 결원이 안 메워짐
- 2~3연속 N 중인 사람을 늘리면 → **4연속 N**이 되어 하드락 3 위반

세 갈래가 전부 막힌다. **나이트는 애초에 2일 이상 묶어서만 성립하는 근무**라, 1열(y축)만으로는 원리적으로 채울 수 없다.

### 5.5 실험 4 — 연쇄 깊이를 늘리면 되는가

해결불가 60건 표본에 깊이를 3 → 4 → 5 로 올려 측정:

| 연쇄 깊이 | 해결 |
|---|---|
| 3인 | 0 / 60 |
| 4인 | 0 / 60 |
| 5인 | 0 / 60 |

**깊이를 늘려도 한 건도 해결되지 않는다.** 사람을 더 끌어와도 §5.4 의 세 갈래는 그대로 막혀 있기 때문이다. 이것으로 y축 접근의 경계가 확정됐다:

> **D·E 결원은 y축(당일 1열)으로 96% 이상 해결된다.**
> **N 결원의 3분의 2는 y축으로 풀 수 없고, 이웃 날짜까지 여는 x축 확장이 있어야 한다.**

이는 알고리즘 결함이 아니라 **문제의 구조**다. 나이트 결원은 연쇄를 깊게 파는 게 아니라 축을 바꿔야 한다.

### 5.6 실험 5 — LNS 로 N 결원을 푸는가 (품질 실측)

§5.5 에서 y축의 한계가 확정됐으므로, 그 구간을 LNS 가 메울 수 있는지 별도로 실측했다.
초기 실측(§1.3)에서 LNS 를 탈락시킨 이유는 "6.5초가 화면에 못 쓸 시간"이어서였는데,
**y축이 못 푸는 25% 구간에 한해서는 6초도 쓸 수 있는 시간**이다.

**실험 설계**

| 항목 | 값 |
|---|---|
| 대상 | y축 해결불가로 분류된 N 결원 3건 (이채윤 08-04, 김준수 08-01, 최성원 08-08) |
| 방법 | 기존 근무표 1,085셀을 baseline 고정셀로 주입, 결원자+후보풀 20명 × [결원일±K] 만 자유변수 |
| K | 1, 2, 3 |
| 품질 기준 | (a) 결원 칸이 실제로 메워졌나 (b) 하드 위반이 원본 대비 늘지 않았나 (c) 변경 셀 수 (d) 시간 |
| 원본 하드 위반 | 1건 (판정 기준선) |

`_run_cp_sat_basic` 을 스크립트에서만 몽키패치해 고정셀을 주입했다.
생성된 schedule 은 명시 DELETE 로 정리했고(9,774행), 기존 25건은 그대로 남은 것을 확인했다.

> ### ⚠ 이 절의 수치는 **무효다** (§10.2 에서 정정)
> 하네스가 **결원자를 비우지 않은 채** 측정했다. 결원 칸을 자유변수로만 두면 솔버가
> 원래대로 배정하므로, 실제로는 "결원이 없는 근무표를 다시 만든 것"에 불과했다.
> `filled == 'N'` 을 "메움"으로 판정해 그걸 성공으로 셌다.
> 결원자를 OFF 로 못박고 다시 재면 **변경 셀 17개 · 7.8초**다(§10.3).
> 아래 표는 기록으로만 남긴다.

**결과 — 9/9 전부 품질 통과 (무효)**

| 케이스 | K | 전체 시간 | solve | 자유 셀 | 변경 셀 | 결원 칸 | 하드 Δ | 판정 |
|---|---|---|---|---|---|---|---|---|
| 이채윤 | 1 | 14.49s | 2.91s | 60 | **8** | 메움(N) | 0 | 품질OK |
| 이채윤 | 2 | 12.52s | 2.86s | 100 | 6 | 메움(N) | 0 | 품질OK |
| 이채윤 | 3 | 14.52s | 3.14s | 140 | 30 | 메움(N) | 0 | 품질OK |
| 김준수 | 1 | 12.41s | 2.71s | 40 | **4** | 메움(N) | 0 | 품질OK |
| 김준수 | 2 | 14.63s | 2.89s | 60 | 11 | 메움(N) | 0 | 품질OK |
| 김준수 | 3 | 18.30s | 3.14s | 80 | 4 | 메움(N) | 0 | 품질OK |
| 최성원 | 1 | 16.21s | 2.71s | 60 | **6** | 메움(N) | 0 | 품질OK |
| 최성원 | 2 | 15.00s | 2.99s | 100 | 9 | 메움(N) | 0 | 품질OK |
| 최성원 | 3 | 12.02s | 3.05s | 140 | 29 | 메움(N) | 0 | 품질OK |

**해석**

1. **LNS 는 y축이 못 푸는 N 결원을 실제로 푼다.** 3케이스 × 3K = 9회 모두
   결원 칸이 N 으로 채워졌고, 하드 위반이 원본 대비 늘지 않았다(Δ=0).
   §5.4 에서 확인한 "나이트는 2일 이상 묶어야 성립한다"를 LNS 가 ±K 일을 열어 해결한다.

2. **K=1 이 최적이다** ← **틀렸다.** 결원자를 고정하지 않은 무효 측정 기반이었다.
   165건 전수로 다시 재면 K=1 은 56.4%, **K=3 이 98.2%** 다(§10.6).

3. **시간은 12~18초로 측정됐다.** 현재 구현(전용 CP-SAT)은 중앙 **143ms** 다(§10.6).
   solve 구간은 2.7~3.1초로 일정한데 나머지 10~15초가 전부 고정비다.
   고정비는 병동 규모·데이터량에 비례하므로 **병동마다 다르다**.
   앞서 관찰한 "고정비는 자유변수를 줄여도 안 줄어든다"가 여기서도 그대로 확인된다.

4. 따라서 LNS 는 **즉답 경로로는 여전히 부적합**하지만,
   y축이 실패한 25% 구간의 **후속 경로로는 유효**하다.

### 5.7 실험 6 — CP-SAT 없이 N 결원을 풀 수 있는가 (실패한 시도)

LNS 는 부작용(Schedule 생성·푸시 발송) 때문에 배선이 까다롭다(§4.8).
그래서 **CP-SAT 를 아예 안 쓰는 길**을 먼저 시도했다.

**가설** — LNS 실측이 실제로 알려준 건 "나이트는 2일 이상 묶여야 성립한다" 이고,
K 를 좁게 잡아도 된다는 뜻으로 읽었다(그 판단 자체는 §10.6 에서 K=3 으로 정정됐다).
그렇다면 후보를 `(결원일, N)` 한 칸이 아니라 `(결원일, N) + (인접일, N)` **2일 블록**으로
배정하면, 기존 y축 체커만으로 같은 효과를 낼 수 있지 않을까.

**1차 측정 — 84.8%. 그러나 틀린 수치였다**

```
2일 블록으로 새로 풀림   140/165건 (84.8%)
속도                    중앙 2.5ms · 최대 3.0ms
인접일 인원 초과         321건 (9/8)
```

"인접일 인원 초과 321건"이 이상해서 검사 코드를 다시 봤다.
후보가 인접일에 근무 중일 때(`E→N`) **그 사람이 떠난 E 의 인원이 줄어드는 것을 검사하지 않았다.**
초과(N 9/8)만 세고 부족(E 7/8)은 안 본 것이다.

**2차 측정 — 인접일 커버리지를 걸자 0건**

```
2일 블록으로 새로 풀림   0/165건 (0.0%)
```

**한 건도 안 풀린다.** 이 병동은 35명에 D8/E8/N8 요구라 여유가 없어,
후보가 인접일에 근무 중이면 그 근무가 반드시 부족해진다.
후보가 인접일에 OFF 라면 결원일에도 OFF 일 텐데, 그러면 2N 뒤에 OFF 2일이 필요해
회복 규칙(하드)에 걸린다. 양쪽이 다 막힌다.

**3차 측정 — 인접일 연쇄를 1단계 붙여도 4.8%**

```
2일 블록 + 인접일 보충   8/165건 (4.8%)
속도                    중앙 4.3ms · 최대 15.4ms

[N 결원 종합] 전체 248건
  y축 1칸        83건 (33.5%)
  2일 블록 추가  + 8건
  합계           91건 (36.7%)
```

해결된 8건도 전부 `최성원 08-30 O→N + 08-29 E→N` 하나의 패턴에 몰려 있다.
월말 경계라 뒤쪽 제약이 없는 특수 케이스다.

**결론 — 이 방향은 실패다.**

나이트 결원은 **여러 사람의 여러 날을 동시에 재배치**해야 풀린다.
연쇄 깊이를 더 파면 조금 더 늘겠지만, 그건 CP-SAT 가 하는 일을 손으로 재구현하는
방향이고 조합이 폭발한다. LNS 가 **11명 17셀**을 동시에 재배치해야 풀어낸다는 것이(§10.3)
그 증거다 — 사람 손으로 재현할 규모가 아니다.

> **교훈**: 1차 84.8% 는 검사 항목이 빠져서 나온 수치였다.
> 커버리지처럼 **양방향(초과/부족)이 있는 제약은 한쪽만 세면 반드시 낙관 편향이 생긴다.**
> 이상해 보이는 부수 지표("초과 321건")가 그걸 잡아냈다.

### 5.8 실험 7 — 기존 추천은 지금 기준으로 정상 기대값을 내는가

§1.2 에서 기존 구현의 한계를 **코드를 읽고** 지적했다("감점만 한다").
실제로 그런지 데이터로 확인했다.

**방법** — 같은 결원 케이스를 두 경로에 넣고 대조한다.

```
(A) 기존  recommend_replacement_candidates  → top-5 후보 목록
(B) 신규  replacement_chain_service         → 솔버 하드 규칙 판정

(A) 가 추천한 후보를 (B) 로 재검사 →
    솔버가 하드로 막는 사람을 기존이 추천하고 있는가?
```

표본: 전체 744건에서 균등 추출한 60건 × top-5 = 후보 300명.

**결과**

| 지표 | 값 |
|---|---|
| 기존 추천 후보 중 하드 위반 | **267 / 300명 (89.0%)** |
| **1순위(rank 1) 후보가 하드 위반** | **52 / 60건 (86.7%)** |
| 기존이 "후보 없음"이라 한 건 | 0건 — 기존은 거의 항상 뭔가를 추천한다 |

**위반 사유 분포**

```
 146명  연속근무 초과
  28명  단일 나이트(1N)
  26명  금지전환 E→D
  23명  월 나이트 개인한도 초과
  16명  N 직후 OFF 미부여(회복)
  10명  금지전환 N→E
   6명  금지전환 N→D
   4명  이미 같은 근무 (대체 효과 자체가 없음)
   3명  등급 최소인원 미달
   3명  커버리지 인원 부족
```

**해석**

1. **1순위가 86.7% 확률로 하드 위반**이다. 사용자가 가장 먼저 보고 누를 값이
   솔버라면 배정하지 않았을 사람이다. "추천"의 의미가 성립하지 않는다.

2. 위반 1위가 **연속근무**인데, 기존 경로의 config(`max_conseq_work=1`)는
   최신(5)보다 **훨씬 엄격**하다. 더 엄격한 기준을 갖고도 후보에 남겼다는 것은
   config 차이 때문이 아니라 **연속근무를 하드로 걸지 않기 때문**이다.
   §1.2 의 `_rule_safety_score` 가 `risk +=` 감점만 한다는 코드 판단이 데이터로 확인됐다.

3. **"이미 같은 근무" 4명** — 그 날 이미 같은 근무를 하고 있어 데려와도
   결원이 안 메워지는 사람까지 추천 목록에 있다. §6.1 에서 내 프로토타입이
   저질렀던 것과 같은 실수가 기존 코드에도 있다.

4. 기존이 "후보 없음"을 낸 케이스가 0건이다. **항상 뭔가를 내놓는다** —
   실제로는 해가 없는 N 결원 24.6% 에서도 후보를 제시한다는 뜻이다.

**함의 — 신규 모듈을 붙이는 것만으로는 해결되지 않는다**

신규 수정안은 `chain_results` 라는 **별도 필드**로 붙었고 기존 `results`(candidates)는
그대로였다(§4.6). 화면이 기존 목록을 계속 노출하면 사용자는 여전히 하드 위반 후보를 본다.

→ **§5.9 에서 기존 목록에도 하드 게이트를 걸어 해소했다.**

### 5.9 실험 8 — 기존 목록에 하드 게이트 적용

기존 스코어링 로직은 그대로 두고, **정렬 전에** 하드 위반 후보를 빼는 게이트를 넣었다.
정렬 뒤에 걸면 `top_k` 자리를 위반 후보가 차지한 채 잘려나가 후보 수가 줄어든다.

표본 40건 × top-5, 게이트 ON/OFF 를 같은 케이스로 대조:

| | 게이트 OFF | 게이트 ON |
|---|---|---|
| 후보 수 | 200 | 37 |
| 하드 위반 후보 | **176 (88.0%)** | **0 (0.0%)** |
| 1순위 위반 | **35/40** | **0/20** |
| 후보 없음 케이스 | 0 | 20 |

**게이트가 뺀 사유** (1,214건 / 13종)

```
280명  이미 같은 근무          ← 데려와도 결원이 안 메워진다
229명  단일 나이트(1N)
158명  월 나이트 개인한도 초과
149명  금지전환 E→D
141명  연속근무 초과
 54명  D 인원 부족    46명  E 인원 부족    36명  N 인원 부족
 38명  금지전환 N→E   34명  금지전환 N→D
```

배제 사유 1위가 **"이미 같은 근무" 280명**이다. 그 날 이미 같은 근무를 하고 있어
**대체 효과가 0인 후보**가 기존 추천의 가장 큰 오염원이었다.

**"후보 없음"이 0 → 20건으로 늘어난 것은 정상이다.**
전수 측정에서 1인 스왑이 가능한 케이스가 59.8% 였으므로, 나머지는 원래 한 명으로는
해결되지 않는다. 기존은 그 사실을 숨기고 위반 후보를 내놓고 있었다.
그 케이스의 답은 **연쇄 수정안**(`chain_results`)이므로,
프론트는 `enforce_hard_rules` 와 `include_chain_proposals` 를 **함께** 켜야 한다.

**교차 검증** — 게이트를 통과한 후보 집합이 신규 경로의 1인 스왑 제안과 **완전히 일치**했다
(불일치 0건). 두 경로가 같은 판정 기준을 쓰고 있음을 확인한 것이다.

**롤백 스위치** — `enforce_hard_rules` 를 `False` 로 두면 과거 동작 그대로다
(위반 176명 유지). 장애 시 되돌릴 수 있도록 남겼고 평상시 끄지 않는다.

**비용** — 게이트 ON + 수정안 포함이 2,574ms, OFF 가 1,394ms.
차이 약 1.2초는 판정 재료 로드다. 게이트와 수정안이 같은 컨텍스트를 공유하므로
한 번만 낸다(§4.6 의 opt-in 설계를 게이트까지 확장).

### 5.10 결론 — 2단 하이브리드

| 단계 | 방식 | 시간 | 커버리지 | 화면 처리 |
|---|---|---|---|---|
| 1단 | y축 스윕 + 연쇄 | **26ms** | 67.2% (1인 43.5% + 연쇄 23.7%) | 즉시 표시 |
| 2단 | 전용 CP-SAT (결원일~+3일·최대 6칸) | **72ms** | 1단 실패분 13.0% | 즉시 표시 가능 |

1단이 D·E 결원을 96% 이상 즉시 처리하고, 2단이 나이트 결원을 맡는다.
두 경로 모두 같은 하드/소프트 기준(§3)으로 판정하므로 결과가 서로 모순되지 않는다.

## 6. 실험 과정에서 잡은 결함 (정정 기록)

### 6.1 이미 같은 근무 중인 후보를 "스왑 가능"으로 계상

초기 프로토타입(`yaxis_full.py:301`)이 `cur_main == tgt_main` 을 걸러내지 않았다.

```python
if cur in work_ids and cur_main != tgt_main:   # 같으면 그냥 passed 로 떨어짐
```

D 결원에 **이미 D 근무 중인 사람**이 "1인 스왑 가능"으로 집계됐다. 옮겨봐야 결원이 안 메워지는 무의미한 이동이다.

- 잘못된 보고: 통과 7명 (이채윤·조강희·민지혜·윤지희·강유진·마소희·정나래A)
- 실제: **1명** (윤지희). 나머지 6명은 당일 이미 D 근무 중

이후 스윕에 `if cur_main == main: continue` 를 넣어 수정했다.

### 6.2 절대 판정 → 원본 대비 판정

§5.3 에 전 과정을 적었다. 해결불가 75.3% → 24.6%.
**교훈**: 재검증 기준을 세우기 전에 원본의 위반 상태를 먼저 측정해야 한다. 안 그러면 기존 문제를 제안 탓으로 돌린다.

### 6.3 솔버 디폴트 불일치 3건

§4.2 표. 특히 `banned_day_after_eve` 는 솔버에선 True 인데 대체추천 쪽 디폴트가 False라 **E→D 를 검사조차 하지 않고 있었다**.

### 6.4 하드/소프트 분류 기준을 두 번 고쳤다

**1차 (초기)**: 모든 규칙을 하드 게이트로 걸었다.

**2차 (오분류)**: "법규만 하드, 내규는 소프트"로 해석하고 사람 판단으로 나눴다.
근로기준법 근거를 찾아 전환 규칙(N→D, E→D, N→E)과 주휴일을 법규(하드)로,
연속근무·나이트 회복·1N 금지·커버리지·등급을 내규(소프트)로 내렸다.
→ **기준이 틀렸다.** 법규냐 내규냐를 사람이 판단할 문제가 아니었다.

**3차 (확정)**: **솔버에서 하드로 계산되면 대체에서도 하드, 소프트면 소프트.**
근무표를 만든 주체가 솔버이므로, 대체 판정이 솔버와 다르면
"생성은 되는데 대체는 안 되는" 모순이 생긴다.

3차 기준으로 코드를 읽은 결과가 §3 이다. 중간에 한 번 더 함정이 있었다 —
`fallback_lex.py:1455` 의 주석이 `# 2) 안전/법규 위반(정량 슬랙) 구성` 이라
전환·연속근무·회복이 전부 소프트로 보였다. 실제로는 해당 슬랙 리스트가
**한 번도 채워지지 않고** `m.Add` 하드로 강제되고 있었다(§3.2).

> **교훈**: 주석과 자료구조 선언만으로 하드/소프트를 판정하면 안 된다.
> 슬랙 리스트가 실제로 채워지는지, 목적함수에 들어가는지까지 확인해야 한다.

최종적으로 **초기 구현에서 실제로 틀린 것은 상호배제 하나**였다(§3.4).
따라서 §5 의 측정치(N 결원 66.5% 해결불가 등)는 그대로 유효하다.
상호배제를 소프트로 내린 뒤 전수 재측정해도 수치는 동일했다 —
이 병동에 상호배제 쌍이 설정돼 있지 않아 판정에 걸리는 케이스가 없었기 때문이다.

### 6.5 위반 델타를 문자열 집합 차집합으로 계산한 오류

§2.2 의 `V(x) \ V(x0)` 를 구현할 때 위반 **메시지 문자열**의 집합 차집합을 썼다.
그런데 메시지에는 일수와 날짜가 박혀 있다:

```
"순수 OFF 5연속(4연속 금지)"      ← 원본
"순수 OFF 4연속(4연속 금지)"      ← 제안 적용 후 (한 칸 줄어 완화됨)
```

문자열이 다르므로 차집합에 남고, **위반이 완화됐는데도 "새 위반"으로 잡혀 후보가 배제됐다.**
`_streak_warnings` 의 `"연속근무 7일(2026-08-01~2026-08-07) — 최대 6일 초과"` 도 같은 구조다.

4O 규칙을 추가한 직후 1인 스왑이 445 → 437 로 8건 줄어 발견했다.

**수정** — 규칙 종류별 건수 증가분만 새 위반으로 센다:

```python
def _kind(msg: str) -> str:
    """위반 메시지 → 규칙 종류 키. 일수·날짜를 지운다."""
    s = _RE_PAREN.sub("", msg).split("—")[0]
    return _RE_NUM.sub("#", s).strip()


def delta_violations(before_msgs, after_msgs) -> list[str]:
    b = Counter(_kind(m) for m in before_msgs)
    a = Counter(_kind(m) for m in after_msgs)
    return [k for k, n in a.items() if n > b.get(k, 0)]
```

수정 후 437 → 445 로 복구됐다.

> **교훈**: 사람이 읽으라고 만든 메시지를 판정 키로 쓰면 안 된다.
> 규칙 종류와 표시 문구를 분리하거나, 최소한 정규화해서 비교해야 한다.

### 6.6 주말휴무를 아예 안 보고 있었다 — 검증 병동이 가려 준 결함

**발견 경위** — 사용자가 "기존 근무자의 근무유형과 주말휴무 적용 여부도 계산돼야 하지 않나"

**솔버는 양방향 하드로 건다** (`fallback_lex.py`)

```python
if getattr(cfg, "weekend_off_only_enable", True):     # 디폴트 True
```

"전 요건 충족"이라고 보고했지만 실환경 41.6% 에서 어긋날 수 있는 상태였다.

**수정** — `ChainContext` 에 `weekend_off` / `weekend_days` 를 싣고 하드 검사에 추가했다.

```python
def _weekend_off_violations(nurse_id, day, shift, ctx):
    if nurse_id not in ctx.weekend_off:
        return []
    is_weekend = day.day in ctx.weekend_days
    if is_weekend and shift in ctx.categories["work"]:

    if not is_weekend and shift not in ctx.categories["work"]:

    return []
```

### 6.7 마지막 하드 규칙 2종을 안 보고 있었다 — 팀 최소인원 · 관할일

- 등급 제약이 느슨한 병동이라 등급 관련 코드 경로가 얕게만 실행됐다.
- 상호배제 쌍이 이 병동에 설정돼 있지 않아, 소프트 전환의 효과를 실측으로 확인하지 못했다.
- LNS 품질 실측은 3케이스 × 3K = 9회다. y축 해결불가 183건 전체를 돌린 것이 아니다.
- 미검사 규칙 3종(§3.5)이 있어, 현재 "전 요건 충족"은 **구현된 규칙 범위 안에서**의 충족이다.

## 8. 단일모드(SINGLE) 확정 사양

> **이번 작업의 적용 범위는 SINGLE 모드 하나다.** 이 절만 읽으면 무엇이 확정됐고,
> 어떤 흐름으로 동작하며, 프론트가 무엇을 하면 되는지 알 수 있도록 정리했다.
> 아래 JSON 은 전부 dev 실 DB(`schedule_id = a9c34dcf5985`, 중환자실1 2026-08)
> 에서 실제로 받은 응답이며 손으로 지어낸 값이 없다.

### 8.1 적용 범위 — 확정

| 대상 | 상태 | 근거 |
|---|---|---|
| **SINGLE 모드** (결원 1칸) | **적용** | 이번 작업 범위 |
| BULK 모드 (결원 기간) | 미적용 | `_recommend_bulk_markov` 별도 경로. 여러 날을 한꺼번에 비우면 슬롯 독립 평가가 틀린다 |
| y축 1열 + 연쇄(최대 3인) | **적용** | §2.3 · §2.4 |
| **2단 전용 CP-SAT** (나이트 결원) | **적용** | §10. 1단 실패 시에만 · opt-in · **143ms** |

### 8.2 확정 정책

| # | 정책 | 확정 내용 | 근거 |
|---|---|---|---|
| P1 | **하드/소프트 판별 기준** | 사람이 법규·내규로 나누지 않는다. **솔버(`fallback_lex`)가 `m.Add` 로 강제하면 하드, 슬랙으로 최소화하면 소프트** | §3.1~3.3 |
| P2 | **위반 판정식** | 절대 무위반이 아니라 **원본 대비 악화 금지** (`V(x) \ V(x0) = 공집합`) | §2.2 · §5.3 |
| P3 | **위반 델타 계산** | 메시지 문자열 차집합이 아니라 **규칙 종류별 건수 증가분** | §6.5 |
| P4 | **config 출처** | 그룹 **최신** config (생성기 `_fetch_latest_config` 와 동일). `schedule.config_id` 아님 | §4.7 |
| P5 | **하드 위반 후보** | 목록에서 **제외**한다. 감점 처리하지 않는다 | §5.8 · §5.9 |
| P6 | **소프트 위반** | 제외하지 않고 **감점 + `soft_warnings` 노출**. 사용자가 판단한다 | §2.7 |
| P7 | **제안 정렬** | `(참여 인원 수, 점수)` 오름차순. MPP 목적을 사전식 우선 | §2.7 |
| P8 | **적용(쓰기) 경로** | 새 엔드포인트를 만들지 않는다. `moves` 를 그리드에 반영 후 기존 `POST /save` | §4.5 |
| P9 | **기본 스위치** | `enforce_hard_rules` **기본 ON**(결함 수정), `include_chain_proposals` **기본 OFF**(비용) | §4.6 · §5.9 |
| P10 | **해가 없으면 없다고 한다** | 후보를 억지로 만들지 않는다. 전수 기준 24.6% 는 실제로 해가 없다 | §5.4 · §5.9 |

### 8.3 요청 / 응답 계약

**요청** — `POST /roster/replacement/recommend`

```jsonc
{
  "schedule_id": "a9c34dcf5985",
  "mode": "SINGLE",
  "target_nurse_id": "197466",        // 결원 당사자
  "slots": [                          // SINGLE 은 보통 1개
    { "date": "2026-08-01", "shift": "E" }
  ],
  "top_k": 3,
  "options": {
    "enforce_hard_rules": true,       // 기본 true  — 하드 위반 후보 제외
    "include_chain_proposals": true,  // 기본 false — 수정안(1단)까지 원하면 true
    "chain_proposal_limit": 3,
    "include_lns_fallback": false     // 기본 false — 1단이 빈손일 때 2단. 중앙 143ms
  }
}
```

**응답** — 기존 필드는 그대로고 `chain_results` 만 새로 붙는다(하위호환).

```jsonc
{
  "schedule_id": "...", "mode": "SINGLE", "target_nurse_id": "197466",
  "results": [ { "slot": {...}, "recommendation_status": "OK|LIMITED|NONE",
                 "candidates": [...],          // 1인 대체 후보 (게이트 통과분)
                 "excluded_summary": {...} } ],
  "chain_results": [ { "slot": {...}, "proposals": [...] } ],  // 수정안
  "metadata": { "chain_proposals_included": true, ... }
}
```

**`ChainProposal` 필드**

| 필드 | 의미 |
|---|---|
| `rank` | 1부터. 낮을수록 권장 |
| `kind` | `SINGLE_SWAP`(1명) / `CHAIN`(같은 날 여러 명) / `LNS`(인접 일자까지 재배치) |
| `participant_count` | 결원자를 뺀 이동 인원 수 |
| `changed_cell_count` | 결원 처리를 **포함**해 바뀌는 셀 수 |
| `score` | 소프트 점수. 낮을수록 우선 |
| `moves[]` | 적용할 셀 변경 목록. **순서대로** 적용한다 |
| `soft_warnings[]` | 솔버가 소프트로 두는 규칙의 신규 위반. **배제 사유가 아니라 참고용** |

**`ChainMove` 필드**

| 필드 | 의미 |
|---|---|
| `nurse_id` / `name` | 대상 간호사 |
| `date` | 대상 일자 |
| `from_shift` → `to_shift` | 바꿀 근무코드 |
| `is_absence` | `true` 면 **결원 당사자를 비우는 이동**. 사용자가 요청한 결원 처리 자체다 |

### 8.4 처리 플로우

```
[1] 요청 수신 — SINGLE, target_nurse_id, slot(date, shift)
      │
[2] 판정 재료 로드 (요청당 1회, 약 0.9~1.3초)
      │   근무열 · config(최신) · 근무코드 · 등급 · 허용근무형 · 고정근무
      │   주휴 · 월한도 · 상호배제 · 확정원티드 · 기피근무
      │   ※ enforce_hard_rules 또는 include_chain_proposals 중 하나라도 켜져야 로드
      │   ※ 게이트와 수정안이 같은 컨텍스트를 공유 — 비용은 한 번만
      │
[3] 기존 후보 평가 (변경 없음)
      │   나이/자격/파견/스코프 등 기존 배제 → candidate_pool
      │
[4] ★하드 게이트  ← 신규. 정렬 "전"에 건다
      │   후보별로 "그 칸에 넣었을 때 새로 생기는 하드 위반" 계산
      │   위반 있으면 제외 + excluded_summary["hard_rule:<사유>"] 누적
      │   ※ 정렬 뒤에 걸면 top_k 자리를 위반 후보가 차지한 채 잘려 후보가 준다
      │
[5] 기존 스코어링·정렬·top_k  (변경 없음)
      │
[6] ★1단 수정안 (y축)  ← 신규. opt-in. 27ms
      │   스윕   : 빈 칸을 메울 후보 추림           → SINGLE_SWAP
      │   연쇄   : 후보가 비운 자리에 스윕 재귀      → CHAIN (최대 3인)
      │   재검증 : 결과 상태로 통째로 재검사         → 이동 간 간섭 차단
      │   점수   : 소프트 위반 감점 + (인원수, 점수) 정렬 + 중복 제거
      │
[7] ★2단 전용 CP-SAT  ← 1단이 빈손 + include_lns_fallback=true 일 때만. 143ms
      │   결원일~+3일만 변수로 세운다(과거는 열지 않는다). 생성 파이프라인을 안 탄다
      │   결원자 그 칸은 OFF 로 못박음 (안 하면 솔버가 원래대로 배정한다)
      │   목적 = 변경 셀 최소화(MPP) · 상한은 전부 원본 대비 상대화
      │   변경 최대 6칸 하드. 결과를 1단과 같은 체커로 재검증 → 물면 제안 없음  → LNS
      │
[8] 응답 — results(후보) + chain_results(수정안)
      │
[9] 프론트 — 사용자가 안 선택 → moves 를 그리드에 반영 → 기존 POST /save
```

#### S3 — 어느 쪽도 불가 (24.6%)

`신솔희(197466)` 2026-08-02 `E` 결원

```jsonc
"recommendation_status": "NONE",
"candidates": [],
"chain_results[0].proposals": [],
"excluded_summary": {
  "hard_rule:이미 같은 근무": 7,
  "hard_rule:D 인원 #/#": 6,
  "hard_rule:N 인원 #/#": 1, ...
}
```

**정직하게 "없다"고 답하는 것이 정상 동작이다**(P10).
화면은 `excluded_summary` 로 "왜 없는지"를 보여주고 수동 조정으로 안내한다.
나이트 결원이면 대부분 여기 해당한다. **`include_lns_fallback: true` 를 켜면 2단 LNS 가
이 구간을 받는다**(§10.6) — 중앙 72ms · 5셀이며 2열에 걸친다.

#### S4 — 게이트가 실제로 무엇을 막는가

`신솔희` 2026-08-01 `E` 결원, 같은 케이스를 게이트만 바꿔 호출

```jsonc
// enforce_hard_rules = false  (과거 동작)
"recommendation_status": "OK",
"candidates": [
  { "rank": 1, "name": "엄가혜", "current_assigned_shift_code": "E",
    "final_score": 74.449 },      // ★ 그날 이미 E 근무 중인데 1순위
  { "rank": 2, "name": "김해수", "current_assigned_shift_code": "O",
    "final_score": 38.5 },
  { "rank": 3, "name": "민지혜", "current_assigned_shift_code": "O",
    "final_score": 35.0 }
]

// enforce_hard_rules = true  (현재 기본값)
"recommendation_status": "LIMITED",
"candidates": [
  { "rank": 1, "name": "김해수", "final_score": 38.5 },
  { "rank": 2, "name": "민지혜", "final_score": 35.0 }
]
```

**엄가혜는 그날 이미 `E` 근무 중**이라 데려와도 결원이 안 메워진다.
그런데 `final_score 74.4` 로 2위(38.5)의 **두 배 점수를 받아 1순위**였다.
기존 스코어링이 "그 근무를 할 수 있는 사람"을 높게 치면서, 정작
"이미 하고 있어서 대체가 안 된다"를 걸러내지 않은 결과다.
게이트가 이 유형을 표본에서 **280명** 제거했다(배제 사유 1위).

### 8.8 프론트 연동 체크리스트

1. **두 옵션을 함께 켠다** — `enforce_hard_rules: true` + `include_chain_proposals: true`.
   게이트만 켜면 절반이 `NONE` 이라 막힌 것처럼 보인다(S2 가 그 예).
2. **`candidates` 가 비어도 `chain_results` 를 확인**한다. S2 는 후보 0명인데 답이 있다.
3. **`moves` 는 순서대로 적용**한다. 첫 항목은 보통 `is_absence: true`(결원 처리)다.
4. **적용은 기존 `POST /save`** — 그리드에 반영 후 저장. 새 엔드포인트 없음.
5. **`soft_warnings` 는 경고로만 표시**한다. 배제 사유가 아니다. 사용자가 감수하고 고를 수 있다.
6. **`NONE` 일 때 `excluded_summary` 를 노출**한다. `hard_rule:` 접두어가 붙은 항목이
   솔버 규칙에 의한 배제이며, 사용자에게 "왜 없는지"를 설명하는 유일한 근거다.
7. **`changed_cell_count` 를 미리 보여준다** — 연쇄 안은 여러 사람의 근무가 바뀌므로
   적용 전에 몇 칸이 바뀌는지 알려야 한다.
8. **`kind: "LNS"` 는 다르게 다룬다** — 1단은 **같은 날짜 1열**에서 2~4셀만 바뀌지만
   LNS 는 **결원일과 그 다음날 2열**에 걸쳐 중앙 5셀(최대 6셀)이 바뀐다.
   변경 목록 전체를 펼쳐 보여주고 확인을 받아야 한다.
9. **2단도 즉시 응답이다** — 중앙 143ms · p95 224ms. 진행 표시는 있으면 좋지만 필수는 아니다.
   폴백(생성 파이프라인)은 제거했다 — 과거를 열고 상한도 못 걸어 쓸 수 없다(§10.8).

### 8.9 알려진 차이 · 주의

**(1) `candidates` 와 `chain_results` 의 정렬 기준이 다르다**

- `candidates` : 기존 `_final_score` 내림차순 (공정성·선호도·등급적합 반영)
- `chain_results` : `(참여 인원 수, 소프트 점수)` 오름차순

S1 에서 `candidates` 1순위는 김해수(38.5)인데 수정안 1순위는 정아영이다.
**집합은 같지만 순서가 다르다.** 1인 스왑 안이 전부 동점(`score 3.0`)이라
수정안 쪽 내부 순서가 사실상 임의적이기 때문이다.

→ 프론트는 **1인 스왑의 우선순위를 `candidates` 순서로 표시**하는 것을 권한다.
   `chain_results` 는 연쇄 안(그리고 적용할 `moves`)을 얻는 용도로 쓴다.
→ 코드로 일원화하려면 수정안 동점 정렬에 `_final_score` 를 태워야 한다. §7.2 등록 대상.

**(2) 게이트를 켜면 "후보 없음"이 늘어난다 — 정상이다**

표본 40건에서 0건 → 20건. 전수 기준 1인 스왑 가능은 59.8% 이므로
나머지는 원래 한 명으로 안 되는 케이스다. 기존은 그 사실을 숨기고
위반 후보를 내놓고 있었다(§5.8).

**(3) 나이트 결원은 1단으로 대부분 해결되지 않는다 — 2단이 받는다**

N 의 1단 해결률은 33.5% 다. y축(당일 1열)의 원리적 한계이고 연쇄 깊이를 늘려도 안 된다(§5.5).
CP-SAT 없이 2일 블록으로 우회하려는 시도도 실패했다(§5.7).
1단으로는 못 풀며 **2단 LNS 가 이 구간을 받는다**(§10). 2단도 못 풀면 수동 처리다.

**(4) `enforce_hard_rules=false` 는 장애 대응용이다**

과거 동작(위반 후보 노출)으로 되돌아간다. 평상시 끄지 않는다.

**(5) BULK 모드에는 아무 것도 적용되지 않았다**

`_recommend_bulk_markov` 는 별도 경로이며 게이트도 수정안도 붙지 않았다.
BULK 를 쓰는 화면이 있다면 여전히 하드 위반 후보를 노출한다.

**(6) 검증 범위 — 병동이 안 쓰는 기능은 가려진다**

수치는 단일 병동(중환자실1) 2026-08 기준이다. 병동마다 설정이 달라 비율은 달라질 수 있으나,
"하드를 감점으로만 처리한다"는 구조적 결함은 병동과 무관하다.

다만 **그 병동이 안 쓰는 규칙은 전수를 돌려도 한 줄도 실행되지 않는다.**
주말휴무가 실제로 그랬다 — 중환자실1 대상자 0명이라 744건을 다 돌려도 검사가 안 됐고,
지적을 받고서야 발견해 대상자가 있는 병동에서 따로 검증했다(§6.6).
남은 미검사 규칙 3종(팀 최소인원 / 프리셉티 동반 / 파견 관할일)도 같은 위험이 있다.

**(7) banned_wanted(기피근무)는 별도 분석이 필요하다**

`_load_banned` 로 읽어 하드 배제에 쓰고는 있으나, 입력 경로·반영 정책·솔버 기대값·
후속 체커 동작을 아직 전수 확인하지 않았다. 특히 **잔여 선택지 계산**에
`allowed_shifts` × 주말휴무 × banned 를 함께 넣어야 한다
(예: 주말휴무자·DEN 허용·금요일 N banned → 금요일은 D·E 만 가능).
긴급대체와 별건 과제로 §7.2 에 최우선 등록했다.

## 9. banned_wanted(기피근무) 분석 및 수정 — 별건 과제

> 긴급대체와 별건이다. 조사에서 드러난 결함이 커서 같은 문서에 붙여 둔다.

### 9.1 전체 플로우

```
[입력]  POST /wanted/adjustment              ← 원티드관리보드 단일 경로
```

### 9.2 발견한 결함 (전부 실측)

| # | 결함 | 실측 근거 |
|---|---|---|
| ① | `no_option_left` 가 **주말휴무를 안 봄** | 4건 — 김보영·오정운(주말휴무 대상자) 주말 `O` 금지 / 평일 근무 전부 금지가 **통과**하는데 실제 배정 옵션은 0 |
| ② | `allowed_shifts` 를 **캐시 컬럼에서 직접 읽음** | 2명 — 윤수빈·정유신 캐시 `[]` vs as-of `['D','E','N']`. 캐시가 비면 "제한 없음"으로 봐 실제보다 관대해진다 |
| ③ | **`fixed_shift` 미반영** | 김보영 `MID`, 오정운 `D2` — 고정근무자는 그 코드만 가능한데 계산에 없다 |

**④가 가장 컸다.** 관리자가 `'주'` 를 금지로 저장하면 화면에는 저장됐다고 나오는데
근무표 생성에는 **아무 효과가 없었다.** 같은 화면에서 입력하는 fixed 는 정규화되고
banned 만 안 되는 비대칭이었다.

### 9.3 수정 내역

| 대상 | 내용 |
|---|---|
| `wanted_service._assignable_options` (신규) | 잔여 선택지에 **주말휴무 양방향 + fixed_shift** 반영. OFF 를 무조건 옵션에 넣지 않는다 |
| `wanted_service._overlay_allowed_shifts_asof` (신규) | `allowed_shifts`/`fixed_shift` 를 **as-of period** 로 읽는다 |
| `wanted_service._solver_enforceable_codes` (신규) | `{D,E,N,O}` + (`use_mid` 면 `M`). 저장 시 `code_not_enforceable` 로 검증 |
| `roster_create_service._normalize_banned_code` (신규) | `'주'`/`'OFF'` → `'O'`. fixed 경로와 같은 규칙 |
| `roster_create_service._audit_banned_wanted_result` (신규) | 결과 감사 — **경고 로그만**, 생성 차단 없음 |

**사후 검증을 차단으로 만들지 않은 이유** — `_validate_generated_roster` 는 메시지를
반환하면 생성이 통째로 실패한다. 이미 만들어진 근무표를 버리게 되므로 관측만 한다.
솔버가 하드로 걸고 있어 위반 자체가 드물고, 나더라도 원인은 "고정 셀 우선 skip" 이라
데이터 조정으로 풀 문제다.

### 9.4 검증

| 항목 | 결과 |
|---|---|
| as-of 오버레이가 캐시를 덮음 | 정유신 `[]→['D','E','N']` · 윤수빈 `[]→['D','E','N']` |
| 주말휴무 양방향 반영 | 주말 옵션 `['O']` / 평일 옵션 `['D','E','M','N','주']` |
| **수정 전 통과하던 4건이 차단** | 4/4 |
| `fixed_shift` 반영 | 병동 코드계와 불일치(`MID`/`D2`)면 무시 — 과잉 차단 방지 |
| `'주'`/`OFF` → `'O'` | `{'주':'O','off':'O','D':'D','e':'E'}` |
| 주말휴무 아닌 사람 영향 | 없음 |
| 기존 pytest 스위트 | **1,664 passed** |
| 긴급대체 무회귀 | 13/13 |

**부수 발견** — 두 병동 모두 `'M'` 이 "저장돼도 무효였을 코드" 였다.
`use_mid=False` 인데 병동에 `default_shift='M'` 인 근무코드가 존재하기 때문이다.
이제 `code_not_enforceable` 로 저장 단계에서 막힌다.

### 9.5 남은 것

- **`_ward_main_codes` 는 그대로 둔다.** `default_shift` 가 NULL 인 코드(`D2`,`MID`,`HD1`)는
  main 이 없는 코드라 금지 대상이 될 수 없는 게 논리적으로 맞다. 열면 ④와 같은
  "저장은 되는데 무효" 문제가 다시 생긴다.
- **결과 감사는 로그뿐**이다. 위반이 관측되면 응답/화면에 노출할지 결정이 필요하다.
- **BULK 모드 대체추천**에는 여전히 하드 게이트가 없다(§7.2).

## 10. 2단 LNS 구현 (완료)

§4.8 에서 "부작용 때문에 그대로 못 붙인다"고 적었던 것을 구현했다.
선택지 A(생성 파이프라인에 dry-run seam)를 택했다 — B 는 A 를 포함하므로 항상 더 나쁘다.

> **§10.1~10.4 는 1차 구현(생성 파이프라인 dry-run) 기록이다.**
> 지금은 §10.6 의 전용 CP-SAT 모델이 **유일한** 경로다. 이 경로는 §10.8 에서 제거했다.
> 수치도 §10.6 이 최신이다.

### 10.1 1차 구현 — 생성 파이프라인 dry-run (§10.8 에서 제거)

**`generate_roster_service` 에 파라미터 2개 추가**

| 파라미터 | 역할 |
|---|---|
| `dry_run` | Schedule 행 생성·`_persist_entries`·푸시 발송을 전부 건너뛰고 `generated` 만 반환 |
| `lns_fixed_cells` | baseline 고정셀. **nurse_id 기반**으로 받아 파이프라인 안에서 엔진 인덱스로 변환 |

**seam 은 2곳뿐이다.**

```
:4535   schedule = _ephemeral_schedule(...) if dry_run else request_schedule_service(...)
:6400   if dry_run: return {"generated": ..., "dry_run": True}      ← _persist_entries 직전
```

재시도·완화 8경로를 그대로 타므로 **품질은 실제 생성과 같다.**
실패 정리 경로의 `db.delete(schedule)` 는 detached 객체라 예외가 나지만
그 자리가 `except: db.rollback()` 으로 감싸여 있어 무해하다.

**진입점** — `replacement_chain_service.recommend_lns_repair()`.
1단(`recommend_chain_proposals`)이 빈손일 때만 부른다.
API 는 `options.include_lns_fallback` (**기본 false**) 로 켠다.

### 10.2 구현 중 잡은 결함 3건

**① 엔진 인덱스를 밖에서 만들어 엉뚱한 사람에게 고정했다**

첫 시도는 `db.query(Nurse).order_by(Nurse.nurse_id)` 로 인덱스를 만들었다.
그런데 엔진 목록 순서는 nurse_id 정렬이 **아니다**.

```
실제 nurse_index_map: 0=신솔희(197466) 1=정아영(271772) 2=김혜원(262330) 3=민지혜(301044)
```

980셀이 엉뚱한 간호사에게 고정돼 **INFEASIBLE**(완화 탐색 597회 후 실패)이 났다.
→ 고정셀을 nurse_id 로 넘기고, 엔진 목록이 확정된 파이프라인 안에서
`_build_engine_nurse_index_map(nurses_for_engine)` 으로 변환하도록 고쳤다.

**② 결원자를 비우지 않아 "대체"가 아니었다 — §5.6 수치를 무효화한다**

결원 칸을 자유변수로만 두면 솔버가 **원래대로 배정한다.**
§5.6 하네스는 `filled == 'N'` 을 "메움"으로 판정했으므로,
결원자가 그대로 근무 중인 결과를 성공으로 셌다. 9/9 는 무효다.

→ 결원자의 그 칸을 **OFF 로 고정셀에 못박도록** 고쳤다.

| | §5.6 (무효) | §10.3 (정정) |
|---|---|---|

### 10.6 전용 CP-SAT 모델로 교체 (2단 재구현)

§10.5 에서 "느린 건 CP-SAT 가 아니라 생성 파이프라인을 통째로 재사용하는 구조"임이
드러났다. 그래서 **생성 파이프라인을 안 타고 전용 모델을 직접 세우도록** 바꿨다.

**왜 가능한가** — 판정 재료가 이미 `ChainContext` 에 다 있다(1단이 쓰는 것과 같다).
추가 DB 접근이 0 이므로 전처리가 통째로 사라진다.

**모델 구성** — 자유 구간(결원일 ±K)만 변수로 세우고 나머지 날짜는 **상수**로 넣는다.

```
변수   x[nurse][date][code]   자유 셀만. 원본이 D/E/N/O 계열인 칸에 한한다
제약   셀        허용근무 · 고정근무 · 주휴 · 주말휴무 · 기피 · 확정원티드
       인원      커버리지 · 등급 최소인원(누적 + cascade)
       시퀀스    전환금지 · 연속근무 · 연속N · 1N금지 · 4O · 회복
       월        나이트 개인 한도
목적   변경 셀 수 최소화 (MPP)
```

| | 이식 전 (`fallback_lex`) | 이식 후 (전용 모델) |
|---|---|---|
| 시간 | 7.8s | **143ms** (55배) |
| 변수 | 12,522 × 3단계 | **1,680** |
| solve 호출 | 7회 | **1회** |
| 전처리 | 3s (N+1 포함) | **0** |
| 변경 셀(중앙) | 17 | **7** |

변경 셀이 줄어든 건 **목적함수에 MPP 를 직접 넣었기 때문**이다.
`fallback_lex` 는 근무표 생성용이라 그런 목적이 없다.

**정확성 보장** — 제약을 이 모듈에서 다시 세웠으므로 모델만 믿지 않는다.
결과를 **1단과 같은 체커**(`hard_violations` + `delta_violations`)로 재검증하고,
물리면 제안하지 않는다(폴백은 §10.8 에서 제거).

#### 만드는 과정에서 잡은 함정 3개

**① 절대 무위반으로 걸면 INFEASIBLE** — 원본 근무표가 이미 하드 위반 13건이라
모델이 원본조차 재현하지 못했다(64ms 만에 해 없음). §5.3 과 같은 함정이다.
모든 상한을 **원본 대비 상대화**했다.

```python
cap = max(kmax, sum(_orig(lm, nurse_id, d, want) for d in window))
m.Add(sum(_term(lm, nurse_id, d, want) for d in window) <= cap)
```

**② 시퀀스 제약을 no-good cut 으로 때우려던 시도는 실패** — 처음엔 커버리지·등급만
모델에 넣고 시퀀스는 사후 검증 + cut 으로 걸러내려 했다. 조합이 방대해 8회 반복으로도
못 잡았고 하드 위반이 13 → **25로 늘었다**. 전환·연속근무·연속N·1N·4O·회복을
**모델에 직접** 넣어야 했다.

**③ 휴가·교육 셀이 근무로 바뀔 수 있었다** — 목적함수가 D/E/N/O 아닌 코드를 무시해
그 셀이 자유롭게 변했다. 모델이 표현 못 하는 코드는 **자유변수에서 제외**했다.

#### 자유 반경 K 재측정 — "K=1 이 최적"은 틀렸다

§5.6 의 K 판단은 결원자를 고정하지 않은 무효 측정 기반이었다.
1단 미해결 N 결원 **165건 전수**로 다시 재면 정반대다.

→ 다만 이 K 는 **과거까지 여는 ±K** 였다. §10.8 에서 `LNS_FORWARD_DAYS = 3`(앞으로만)으로 바뀐다.

## 11. 커버리지 100% 달성 — 최종 구조와 결함 8종

§10 까지의 상태는 **해결 80.2% · 불가 19.8%** 였다. 불가한 케이스는 화면이 빈 채로 나갔다.
이 절은 그 19.8% 를 파고들어 얻은 결과를 기록한다. 결론부터 — **불가의 대부분은 문제가
어려워서가 아니라 우리가 건 제약이 잘못돼서였다.**

### 11.1 최종 탐색 순서

```
① 1단 무위반          당일 1열, 스윕 + 최대 3인 연쇄          27ms
② 2단 무위반          결원일~+3일 전용 CP-SAT, 상한 6칸       53ms
③ 넓힌 2단 무위반  ┐   같은 모델, 상한 12칸                  ├ 함께 담고
   1N 차선안      ┘   1N 금지만 끈 사본으로 1단 재탐색        ┘ 무위반을 위로
④ 대체 불필요         빼도 인원이 요구치를 만족 → 그냥 비우기 (목록 맨 뒤)
```

②를 ③보다 먼저 두는 것이 핵심이다. 순서를 뒤집으면 규칙을 다 지키는 2단 해가 있는데도

어느 쪽이 나은지는 상황에 달렸으므로 둘 다 담고 정렬로 무위반을 위에 올린다.

### 11.2 잡은 결함 8종

전부 실측으로 확인했고, 검증 병동을 바꿔 가며 교차 확인했다.

#### ① 확정 원티드 셀 배제가 무효였다 (1단 19건 · 42병동 84건 유출)

`hard_violations()` 안에 `"확정 원티드 셀"` 을 넣어 뒀는데, `_sweep` 은 before/after **델타**로
판정한다. 같은 `(nurse, day)` 는 양쪽에 똑같이 나오므로 증가분이 0 이 되어 그대로 통과했다.

> **상태 불변 조건**("이 셀은 못 건드린다", "이 사람은 대상이 아니다")은 델타로 표현할 수 없다.
> 후보 선정 단계에서 **절대 배제**해야 한다.

2단은 안 샜다 — `_add_cell_rules` 가 `m.Add(x[n,d,원본]==1)` 로 구조적으로 고정하기 때문이다.
같은 함정을 원티드 제출자 배제에서도 겪었다(820건 유출). 패턴을 알고 나서야 확정 셀 쪽을
의심하게 됐다.

#### ② 등급 최소인원 기준선이 원본이라 INFEASIBLE (가장 컸다)

민지혜 8-09 N 케이스가 어떤 설정으로도 안 풀렸다. 자유 범위 +10일, 상한 무제한, 1N 해제까지
전부 INFEASIBLE. 제약군을 하나씩 끄는 이분 탐색으로 범인을 특정했다.

| 끈 제약군 | 결과 |
|---|---|
| 전체 유지 | INFEASIBLE |
| cell 제외 | INFEASIBLE |
| team 제외 | INFEASIBLE |
| nightquota 제외 | INFEASIBLE |
| **grade 제외** | **OPTIMAL** |
| coverage 제외 | OPTIMAL |
| sequence 제외 | OPTIMAL |

원인은 결원자가 **그 근무의 유일한 저연차**였다는 것이다.

```
N: 원본 8명(저연차 1 = 민지혜) → 결원 후 7명(저연차 0)   target=1
D: 저연차 1명   E: 저연차 1명    ← 어느 쪽을 빼도 그쪽이 0
```

`_add_grade_rules` 가 `min(target, base)` 로 악화 금지를 걸고 있었지만 `base` 가 **원본** 기준이라
"다른 저연차를 반드시 데려와라" 가 됐고, D·E 도 1명뿐이라 빼는 순간 거기가 깨졌다.

**인원과 등급은 기준선이 다르다.** 인원은 결원 칸을 메워야 하므로 원본 수준을 지켜야 하지만,
등급은 결원자가 유일한 저연차였다면 그 요구 자체가 결원으로 이미 깨진 것이고 대체자가 같은
등급일 이유가 없다. 등급·팀을 결원 반영 후(`lm.baseline`) 기준으로 바꾸자 즉시 7칸 무위반 해가
나왔다.

#### ③ 기본 요청에서 CP-SAT 이 한 번도 호출되지 않았다

1단은 설계상 CP-SAT 을 쓰지 않으므로(§5.7), 두 옵션이 꺼진 기본 요청에서는 **CpModel 생성 0회**다.

|---|---|---|---|

꺼 둔 근거는 스키마에 적힌 **"12~18초"** 였는데, 그건 §10.8 에서 제거한 생성 파이프라인 폴백
시절 수치다. 전용 모델로 바꾼 뒤로는 슬롯당 53ms 다. 낡은 수치가 기본값으로 굳어 있었다.

#### ④ 차선안이 개인 규칙 검사를 통째로 건너뛰었다

> **"검사를 건너뛴다" 와 "규칙 하나만 끈다" 는 전혀 다르다.**

1단도 `_relaxed_ctx`(1N 만 끈 사본)로 **똑같이 검사**하게 고쳤다. 교차 검증에서 차선안이

#### ⑩ 숫자 정규화 때문에 "이미 미달인 날 더 줄이는" 안이 통과했다

**Codex 리뷰 게이트가 잡았다(P1).** `delta_violations` 는 메시지의 숫자를 `_kind` 로

델타가 0 이 되어 그대로 통과한다.

영향이 두 군데였다.

- `_absence_only_plan` — 원본이 이미 7/8 인 날 결원으로 6/8 이 되는데도
  "대체 없이 비워도 인원 기준을 만족합니다" 라고 내보냈다
- `_score_and_filter` 의 구조 판정 — 제안이 **결원 근무가 아닌 다른 근무**의 인원을
  7→6 으로 줄여도 통과했다(`_restores_headcount` 는 결원 근무만 본다)

원본이 이미 미달인 날은 드물지 않다 — 실측 **163건**(중환자실1 2026-08 26 ·
52병동 71 · 중환자실1 2026-04 66).

**문자열 비교를 버리고 수치로 바꿨다.** `_structural_metrics` 가 지표별
`(현재값, 요구치)` 를 주고, `_structural_worsened` 가 `value < min(target, was)` 로
악화를 판정한다. 요구치를 이미 못 채우던 항목도 잡힌다.

"대체 불필요" 는 강한 주장이라 **절대 기준**으로 바꿨다 — 결원 후에도 모든 지표가
요구치를 만족해야 한다. 델타로는 이 판정을 안전하게 할 수 없다.

수정 후 커버가 내려간 것은 **이전 수치가 잘못된 통과 덕분이었다**는 뜻이다.

| 병동 | 수정 전 | 수정 후 |
|---|---|---|

| 42병동 2026-05 | 준수 438 + ABSENCE_ONLY 52 | 준수 438 + **차선안 52** |
| 중환자실1 2026-04 | 100% | **96.9%** |

> **`delta_violations` 로 판정할 수 없는 것이 두 종류다.** ① 상태 불변 조건
> (§11.2 ①) ② **수치 지표** — 정규화가 숫자를 지우기 때문이다. 둘 다 델타가 아닌
> 전용 판정이 필요하다.

#### ⑪ 비우기 선택지가 차선안을 가리고, 목록이 차면 스스로 사라졌다

**Codex 리뷰 게이트 2회차(P2·P3).** ⑨·⑩ 을 고치면서 새로 만든 것이다.

**P2 — 차선안 은폐.** 응답을 나눌 때 `hard_warnings` 유무로만 갈랐는데,
`ABSENCE_ONLY` 는 위반이 없어 `clean` 에 들어간다. 그 하나 때문에
`fallback_proposals` 가 통째로 비워져, 실제 대체안(1N 차선안)이 있는데도
"비우세요" 만 나갔다. 42병동 52건이 이 상태였다.

```python
- fallback = [] if clean else [...]
+ has_replacement = any(p.kind != "ABSENCE_ONLY" for p in clean)
+ fallback = [] if has_replacement else [...]
```

숨길지 말지는 **진짜 대체안이 있느냐**로 정해야 한다.

**P3 — solo 자리 미예약.** `plans[:limit]` 로 자른 뒤 붙이므로 제안이 `limit` 개를
채우면 "비우기" 가 사라졌다. `ABSENCE_ONLY` 를 항상 맨 뒤에 준다는 계약과 어긋난다.
자리를 예약하되 `limit` 이 1 이면 대체안을 우선한다.

> **결함을 고치면서 결함을 만든다.** ⑨ 를 고치며 ⑪-P3 을, ⑦(원문 반환)을 고치며
> ⑩(수치 비교 누락)을 만들었다. 수정 뒤에도 리뷰를 다시 돌려야 하는 이유다 —
> 3회차에서야 "지적 없음" 이 나왔다.

#### ⑫ 1N 금지의 **면제 조건**을 하나도 안 보고 있었다

솔버의 1N 금지는 `m.Add(X(n,d,N) <= sum(neighbors))` — 슬랙 없는 하드다.
`safety` 딕셔너리에도 키가 없어 목적함수 기여가 0 이다. **소프트가 아니다.**

그런데 면제가 4개 붙어 있고, 우리 구현엔 하나도 없었다(`fallback_lex:1620~1631`).

| 면제 | 뜻 | 우리 처리 |
|---|---|---|
| `n_max == 1` | 운영자가 "이 사람 월 N 1회" 로 명시 | **반영** |
| 전월 말 N tail > 0 | 1일 N 이 전월과 연속이라 1N 아님 | **반영**(§11.2 ⑬) |
| `d == 0` 이 fixed N | 1일이 고정 N — 아래 설명 | **불필요** |
| 프리셉티 fixed 셀 | 복사된 단독 N 만 방지, 고정분은 존중 | 미반영 |

**`n_max == 1`** — 솔버 주석: "운영자가 월간 한도로 N=1 을 명시한 의도는 default
1N 금지 정책보다 우선한다." DB 전수로 **3건** 쓰인다(`1025603d1c2a` 2026-06).
검증 병동 5곳엔 0명이라 안 보였다.

| | 총 제안 | 무위반 | 후보 게이트 통과 |
|---|---|---|---|
| 미반영 | 2,458 | 1,999 | 1,750 |
| 반영 | **2,589** | **2,130** | **1,881** |

> `limit=1` 로 1순위만 쟀을 때 해결률·준수·차선이 **전부 동일**해서 "영향 없음"
> 으로 넘길 뻔했다. 실제로는 선택지 131 개가 사라지고 있었다.
> **측정 범위를 좁게 잡으면 결함이 0 으로 보인다.**

**`d == 0` 면제는 우리에게 불필요하다.** 솔버가 이 예외를 둔 이유는 두 가지다 —
① 1일 N 이 1N 인지는 전월 말일에 달렸는데 모델이 그걸 모른다 ② 그 셀은 고정이라
못 바꾸는데 제약을 걸면 2일까지 N 이 강제돼 INFEASIBLE 이 된다. 우리는 전월 꼬리를
보므로 ①이 해소되고, 판정이 델타라 원본이 이미 가진 1N 은 상쇄되며, 확정 원티드
셀은 절대 배제라 후보가 되지도 않는다. **그대로 옮기면 오히려 진짜 1N 위반을
눈감아 준다.** 솔버는 "모델을 세울 때 안 막히게" 예외를 두고, 우리는 "이미 만들어진
근무표를 판정" 한다 — 목적이 다르면 같은 예외가 반대로 작용한다.

#### ⑬ 전월 꼬리를 안 봐서 월초 판정이 전부 틀렸다

월 시퀀스만 보고 인접 규칙을 판정했다. **7월 31일을 모르는 채 8월 1일을 판단**한 것이다.

```
성주영: 전월 7/30 N · 7/31 N  →  8/1 D 를 추천했다
   금지전환 N→D (하드락 #2 "절대 불가") + 2N 직후 OFF 아님 (#5)
이나영: 전월 7/31 E  →  8/1 D
   금지전환 E→D (하드락 #2)
김서하: 전월 7/29 N · 7/30 N  →  8/1 D
   2N 직후 OFF 2일째 아님 (#5)
```

**나이트 하고 나온 사람에게 다음날 데이를 주는 추천을 내보내고 있었다.**

| 월초(1~3일) | 제안 | 무위반 | 후보 게이트 |
|---|---|---|---|
| 꼬리 미반영 | 616 | 536 | 144 |
| 꼬리 반영 | **338** | **250** | **45** |

줄어든 278 건은 전부 실제 하드 위반이다. `ctx.prev_tail` 에 전월 마지막 3일을
싣고, 인접 규칙 검사 시 시퀀스 앞에 이어 붙인다(`_with_prev_tail`). `_runs` 가
날짜 인접성으로 구간을 끊으므로 전월 말일과 1일이 자연스럽게 이어진다.

★ **월 카운트 규칙(`_monthly_night_warning`·개인 월 한도)은 전월을 포함하면 안 된다.**
당월 시퀀스로만 센다. 인접 규칙과 카운트 규칙을 같은 시퀀스로 돌리면 월 나이트가
부풀려진다.

로더는 **일괄 조회**다. `off_swap._load_prev_month_tail` 은 간호사당 쿼리라
35명이면 9.8초가 나온다(§10 에서 이미 겪었다).

#### ⑭ 관할 밖(파견·이동·휴직·프리셉티)이 대체자로 샜다

또 **델타 상쇄**다(§11.2 ① 과 같은 함정, 세 번째).

```python
    out.append("관할 밖(파견·이동·휴직·프리셉티)")
```

그 사람이 그날 **이미 근무 중**이면 before/after 양쪽에 나와 델타가 0 이 된다.
반대로 그날 OFF 였으면 after 에만 나와 배제됐다 — **같은 사람인데 그날 근무
여부에 따라 판정이 뒤집혔다.**

| 병동 | 대체자로 쓰인 건 (수정 전 → 후) |
|---|---|
| 1025603d1c2a 2026-05 | **25건 → 0** |
| 102560184a40 2026-06 | **4건 → 0** |

절대 배제로 옮긴 곳은 네 군데 — `hard_violations` 에서 제거, `_sweep`,
`hard_violation_reasons`, `_local_free_cells`(2단).

★ **결원 당사자의 결원일만 예외**다. 그 칸은 비워야 하고, **프리셉티 본인의
긴급대체 요청은 처리돼야 한다**(실측: 관할제한자 본인 요청 337·67·36·12·35건이
그대로 처리된다). "대체자로는 쓰지 않되 요청은 받는다" 가 요구사항이다.

#### ⑯ 승인된 **연차 셀을 근무로** 바꾸고 있었다

`off_swap_enabled` 병동은 초과 OFF 를 연차 코드(`shifts.off_swap_target=True` — `FB`·`T` 등)로
변환해 저장한다(`cp_sat/off_swap.py`). 그 셀은 **승인된 휴가**다.

2단은 `_local_free_cells` 가 `codes`(D/E/N/O)로 걸러 안 건드렸는데 **1단에 같은 필터가
없었다.** `_sweep` 은 `current` 가 무엇이든 후보로 올린다.

```
중환자실1 2026-08 — FB 셀은 근무표 전체에 단 2개
   FB→D 32건 · FB→E 40건   ← 그 2명이 여러 결원에서 반복 차출됐다
```

`_movable_cell` 로 **근무(D/E/N/MID) 또는 휴무만** 대체에 쓰도록 막았다(1단 스윕 ·
당일 대체 최종안 · 기존 추천 게이트 세 곳). 차출 0건, 해결률은 그대로다.

> **같은 규칙이 1단과 2단에 따로 구현돼 있으면 한쪽만 빠진다.** §11.2 ④(차선안이
> 개인 규칙 검사를 건너뜀)와 같은 구조의 실수다. 2단은 모델 제약으로, 1단은 후보
> 필터로 표현되다 보니 대응이 어긋난다.

#### ⑰ 연차 전환이 대체 적용 후 재계산되지 않는다 (미해결)

`postprocess_off_swap` 은 **생성 파이프라인의 마지막 단계**다(`_persist_entries` 직전).
긴급대체는 그 파이프라인을 타지 않고 기존 `POST /save` 로 저장하므로, 적용 후
OFF 개수가 달라져도 연차 전환이 다시 계산되지 않는다.

```
A: O 8개 → 기준 6개 → 2개가 FB 로 전환된 상태로 저장
긴급대체로 A 를 O→D          → O 5 + FB 2 = 휴무 7일
기준대로면 FB 는 1개여야 하는데 2개  ← 연차 1일이 과잉 소진된다
```

⑯ 으로 FB 셀 자체는 안 건드리게 됐으므로, 남은 위험은 **O↔근무 변경으로 OFF
개수가 달라지는 경우**다. 해결하려면 `POST /save` 경로에 후처리를 넣어야 하는데
그 경로는 수동 편집 전체가 쓰므로 영향 범위가 크다. `_load_prev_month_tail` 의
N+1(실측 9.8초)도 함께 손봐야 한다.

#### ⑮ 결원 당사자의 **다른 날짜**까지 바꾸고 있었다

2단(LNS)이 결원자를 자유 셀로 열어 둬서, "8/4 하루 못 나온다" 는 요청에 이런 안이
나왔다.

```
이채윤 08-04 N→O   [결원]
구민정 08-04 O→D
이채윤 08-05 N→D    ← 결원자 본인의 다음날 근무가 바뀐다
이채윤 08-07 O→D    ← 없던 날에 근무가 생긴다
```

08-05 N→D 는 결원으로 깨진 1N 을 정상화하는 것이라 이해할 여지가 있지만,
**08-07 O→D 는 다른 사람의 빈자리를 결원자가 메우는 것**이다. "오늘 못 나온다"
고 한 사람에게 "그럼 7일에 나와라" 를 돌려주는 셈이라 요청 범위를 넘는다.

WIDE 에서 **49건**, 그중 **25건이 근무 추가**였다.

정책 3안을 재고 **A(결원일만)** 로 정했다.

| 정책 | 해결 | 조건 준수 | 차선안 | 결원자 타 일자 변경 |
|---|---|---|---|---|
| C. 제한 없음 | 94.6% | 683 | 21 | 49 |
| B. 근무 추가만 금지 | 94.6% | 682 | 22 | 26 |
| **A. 결원일만** | **94.6%** | 676 | 28 | **0** |

**해결률은 셋 다 같다.** A 의 손해는 조건 준수 7건이 차선안으로 옮겨간 것뿐이다.
결원으로 깨진 1N 등은 고치지 않고 `absence_side_effects` 로 알린다 —
그건 결원 자체의 결과이지 추천이 해결할 몫이 아니다.

`_local_free_cells` 에서 결원자의 결원일 외 셀을 자유 대상에서 뺀다.
1단은 원래 결원자를 `used={target}` 로 제외하므로 무관하다.

### 11.3 차선안 정책

**열 수 있는 것은 1N 금지 하나뿐이다.**

| 항목 | 열 수 있나 | 근거 |
|---|---|---|
| 1N 금지 | **열림** (표시 후 사용자 선택) | 하드락 #7 이지만 사람이 판단하는 긴급 상황 |
| 연속근무 · ND/ED/NE · 연속 나이트 · 3N2O/2N2O | 불가 | 하드락 정책 #1~#5 |
| 필요인원 · 등급 최소인원 · 팀 최소인원 | 불가 | 솔버가 하드 고정 + "환자 안전" 명시(§11.2 ⑤) |
| 확정 원티드 셀 · 고정근무자 · 관할 밖 | 불가 | 상태 불변 조건 → 절대 배제 |

1N 만 열어도 실익의 대부분을 얻는다는 것을 미리 쟀다.

| | 커버 |
|---|---|
| 1N 만 허용 | **97.8%** |
| 하드 전종 허용 | 98.7% |

0.9%p 를 얻자고 안전 규칙 6종을 열 이유가 없다.

**옵션 기본값**

| `chain_proposal_limit` | 10 | 10 | — |

**탐색 범위 — `search_scope`**

화면의 '더 넓게 찾기' 와 1:1 로 대응한다. 어디까지 볼지는 **사용자가 고른다** —
병동 사정과 상황에 따라 답이 달라서 하나로 고정할 문제가 아니다.

| 값 | 날짜 범위 | 변경 상한 | CP-SAT |
|---|---|---|---|
| `SINGLE_DAY` (기본) | 결원 당일 한 열 | 4칸 | **호출 안 함** |
| `WIDE` | 결원일 ~ **+3일** | **12칸** | 호출 |

★ 중간 단계(`ADJACENT` — +3일·6칸)는 뒀다가 **없앴다.** 전수 33,250건에서 해결률이
12칸과 **똑같이 96.0%** 였고 조건 준수만 272건 적었다. 얻는 것 없이 선택지만 늘렸다.

★ 날짜를 더 여는 것은 실측상 효과가 없다 — 자유 구간을 +5일·+7일로 넓혀도 추가
해결이 **0건**이었고, 병목은 "N 을 2연속으로 묶을 여유 칸" 이었다. 화면 라벨도
`당일 4칸` / `+3일 12칸` 으로 칸 수를 그대로 드러낸다 — "더 넓게" 같은 문구는
날짜가 넓어지는 것으로 읽힌다.

**중환자실1 2026-08 전수 744건**

| scope | 해결 | 조건 준수 | 차선안(1N) | 없음 | 셀 최대 | CpModel |
|---|---|---|---|---|---|---|
| `SINGLE_DAY` | 90.3% | 520 | **152** | 72 | **4** | **0회** |
| `ADJACENT` | **100%** | 640 | 104 | 0 | 6 | 272회 |
| `WIDE` | **100%** | **712** | **32** | 0 | 11 | 328회 |

`SINGLE_DAY` 는 변경 폭이 가장 작지만 **차선안이 32건→152건으로 5배 늘어난다.**
2단이 규칙을 지키며 풀던 것을 1N 위반으로 때우게 되기 때문이다. "추천 없음 72건" 과
"위반 감수 152건" 을 함께 감수하는 선택이라는 점을 화면에서 분명히 해야 한다.

**인력에 여유가 있는 병동은 세 값의 결과가 같다.** 42병동·52병동·1025603d1c2a 는
`SINGLE_DAY` 만으로도 100% 다(2단을 아예 안 탄다). 2단이 실제로 일하는 것은
중환자실1처럼 D·E·N 이 요구치와 정확히 맞물린 병동뿐이다.

**응답 — `SlotChainRecommendation`**

```
proposals[]           조건을 다 지키는 안. 이것만 정식 추천이다
fallback_proposals[]  1N 하나만 감수하는 차선안
                      **진짜 대체안이 없을 때만** 채워진다 — ABSENCE_ONLY 는
                      위반이 없어 proposals 에 들어가므로, 그것만 있는 경우를
                      "정식 추천 있음" 으로 보면 차선안이 가려진다(§11.2 ⑪)
blocked_reason        둘 다 비었을 때의 한 줄 사유
blocked_detail        후보별 탈락 사유 집계 {사유: 인원}
```

섞어 두면 화면에서 구분이 안 돼 위반이 있는 안을 그냥 추천으로 오인한다.
**`proposals` 가 비어 있다는 것 자체가 "조건을 지키는 방법이 없다" 는 신호**가 되도록 나눴다.

**결원 당사자는 결원일 한 칸만 바뀐다.** 다른 날짜는 어떤 scope 에서도 안 건드린다(§11.2 ⑮).

`ChainProposal.kind` 에 **`ABSENCE_ONLY`** 가 추가됐다 — 빼도 인원이 요구치를 만족해
대체가 필요 없는 경우다. 목록 맨 뒤에 선택지로만 붙인다. 요구인원은 **최소 안전선**이지
운영 목표가 아니므로, D 에 8명을 배치해 둔 병동에 "요구 3명은 넘으니 비워도 된다" 를
1순위로 밀면 안 된다.

**불가 응답 예시**

```
▸ 8월 9일 결원 반영 인원 D 8/8 · E 8/8 · N 7/8 — 조건을 지키는 대체가 없습니다
     19명  단일 나이트
     12명  월 나이트 개인한도 초과
      7명  금지전환 N→D
      6명  연속근무
```

빈 화면은 "고장났나" 로 읽힌다. 이 정보가 있으면 무엇이 병목인지(위 예시는 월 나이트 한도)
보이고 다음 조치를 판단할 수 있다.

**최소성 — 민지혜 8-09 N 사례**

y축 한 열로는 무위반도 1N 차선안도 **0건**이다. 9일 N 에 1명을 넣으면 그날만 N 이라 1N 이
되고, 피하려면 10일도 N 이어야 하므로 **최소 2열이 강제**된다.

| 셀 상한 | 결과 | | 자유 범위 | 결과 |
|---|---|---|---|---|
| 2~6칸 | 불가 | | +1일 (9,10) | 불가 |
| 7칸 | 해 있음 · 7칸 | | +2일 (9,10,11) | 7칸 |
| 8·10·12칸 | 해 있음 · **7칸** | | +3~5일 | 7칸 |

상한을 올려도 실제 변경은 7칸에 머문다 — `Minimize` 가 최소 해를 낸다. 이 케이스의
구조적 하한은 **3열 × 7칸**이다.

```
민지혜  9일 N→O    결원
정나래A 9일 D→N    N 채움            → 정나래A 9일 D 가 빔
정나래A 10일 D→N   1N 회피(2연속)     → 정나래A 10일 D 가 빔
양다영  10일 N→D   10일 D 메움
엄가혜  9일 O→D    9일 D 메움         → 엄가혜 연속근무 초과
엄가혜  11일 E→O   연속근무 해소       → 11일 E 가 빔
이관희  11일 O→E   11일 E 메움
```

기본 상한 6칸으로는 이 케이스가 여전히 불가다. **확장 단계(12칸)가 받쳐 줘야 풀린다.**

### 11.7 이 절에서 배운 것

**"불가" 를 선언하기 전에 모델을 의심할 것.** 이 세션에서 여러 번 "구조적으로 불가능하다"고
단정했는데, 실제로는 제약 기준선이 잘못된 것이었다(§11.2 ②). 제약군을 하나씩 끄는 이분
탐색을 처음부터 했으면 훨씬 빨리 찾았다.

**검증 병동이 기능을 가린다** — §6.6·§6.7 에 이어 세 번째다. 중환자실1·42병동에서 0 이던
결함이 다른 병동에서 13건·1건씩 나왔다(§11.2 ⑦⑧). 규칙을 건드릴 때마다 **그 규칙을 실제로
쓰는 병동**을 찾아 교차 검증해야 한다.

**리뷰 게이트를 건너뛰지 말 것.** §11.2 ⑨ 는 사람 눈으로 여러 번 읽고도 못 본 것을
Codex 가 한 번에 잡았다. 조기 반환 한 줄이라 diff 에서는 자연스러워 보이지만, 실제로는
106건의 추천을 가리고 있었다. 코드 수정마다 리뷰를 돌린다.
