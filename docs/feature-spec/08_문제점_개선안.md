# 현재 구조의 문제점과 개선 제안

> 코드 분석에서 확인된 사실을 기반으로 진단한다.  
> **"전면 재설계"가 아닌 "현재 코드베이스를 살리면서 구조를 명확하게 만드는 방향"** 을 우선한다.  
> 추정인 경우 "추정"으로 명시한다.

---

## 1. 기능명/책임 모호 문제

### 1-1. Wanted 관련 네이밍 혼란

| 문제 | 상세 |
|------|------|
| **현상** | `Wanted`, `WantedRequest`, `NurseShiftRequest`, `ShiftPreference`, `FixedWantedEntry` — 5개 엔티티가 "선호"라는 하나의 도메인을 표현하지만 이름에서 관계가 드러나지 않음 |
| **영향** | 신규 개발자가 선호 흐름을 이해하는 데 시간 소요. API 호출 순서를 코드에서 역추적해야 함 |
| **근거** | `routers/wanted.py` 20+ 엔드포인트, `routers/preferences.py` 6개 엔드포인트가 같은 도메인인데 분리됨 |

**개선안 (단기)**: 코드 변경 없이 문서/주석으로 관계 명시. 이 문서의 [07_도메인모델.md 6장](07_도메인모델.md)이 그 역할.

**개선안 (중기)**: 라우터 통합 검토
```
/preferences/period      ← Wanted (기간 관리)
/preferences/submit      ← ShiftPreference + NurseShiftRequest + NursePairRequest
/preferences/adjustment  ← FixedWantedEntry (조정판)
/preferences/config      ← WantedConfig (제한 설정)
```

### 1-2. `is_night_nurse` 필드명 오해

| 문제 | 상세 |
|------|------|
| **현상** | `Nurse.is_night_nurse`가 Boolean처럼 보이지만 실제로는 JSON 배열이며, 0/1/2/3 정수 코드로 "허용 근무 유형"을 표현 |
| **영향** | `is_night_nurse=3`이 "야간 전용"이라는 것을 코드를 읽지 않으면 알 수 없음 |
| **근거** | `cp_sat/allowed_shift_types.py:normalize_allowed_shift_codes()` — 0=전체, 1/2=주간, 3=야간전용 |

**개선안**: 컬럼 rename은 마이그레이션 비용이 크므로, 단기적으로:
- Pydantic 스키마에 `Field(description="허용 근무 프로필: 0=전체, 1/2=주간가능, 3=야간전용")` 추가
- 프론트엔드에서 표시 시 한글 라벨 사용

### 1-3. RosterConfig의 과도한 책임

| 문제 | 상세 |
|------|------|
| **현상** | `RosterConfig` 35+ 컬럼에 법규, 내규, UI 설정, 팀 밸런스, 프리셉터, 오프 전략이 모두 혼합 |
| **영향** | 법규 변경과 UI 토글 변경이 같은 버전으로 관리됨. 설정 의도 추적 어려움 |
| **근거** | `app/db/models.py:RosterConfig` — 30+ 컬럼, `app/schemas/roster_schema.py:RosterConfigBase` — 30+ 필드 |

**개선안 (단기)**: 테이블은 유지하되, 스키마/프론트엔드에서 논리적 그룹핑:
```python
class RegulationFields:  # 법규 (변경 드묾)
    max_conseq_work, three_seq_nig, max_nig_per_month, ...

class OperationalFields:  # 내규 (월별 조정 가능)
    min_exp_per_shift, even_nights, shift_priority, ...

class DisplayFields:  # UI (근무표 표시 관련)
    show_level, show_preceptor

class TeamFields:  # 팀 밸런스
    team_balance_enable, team_balance_gauge, team_balance_mode

class PreceptorFields:  # 프리셉터
    preceptor_gauge, preceptee_on, preceptee_shift_count
```

**개선안 (중기)**: `config_json` JSON 컬럼으로 마이그레이션하여 스키마 유연성 확보. 또는 카테고리별 별도 테이블 분리.

## 2. API와 도메인 의미 불명확

### 2-1. 근무코드 CRUD가 POST로 통일

| 문제 | 상세 |
|------|------|
| **현상** | `POST /shifts/add`, `POST /shifts/update`, `POST /shifts/remove` — 생성/수정/삭제가 모두 POST |
| **영향** | RESTful 관례 위반. API 소비자가 의도를 추론하기 어려움 |
| **근거** | `app/routers/shifts.py` — 모든 변경 작업이 POST |

**개선안**: 점진적으로 RESTful 전환
```
POST   /shifts          ← 생성 (기존 /shifts/add)
PUT    /shifts/{id}     ← 수정 (기존 /shifts/update)
DELETE /shifts/{id}     ← 삭제 (기존 /shifts/remove)
PATCH  /shifts/{id}/sequence ← 순서 변경 (기존 /shifts/move)
```
기존 엔드포인트는 deprecated 마킹 후 병행 기간 운영.

### 2-2. 동일 기능의 이중 엔드포인트

| 문제 | 상세 |
|------|------|
| **현상** | 간호사 엑셀 업로드가 2세트 존재: `upload-validate/confirm-upload`(구버전) + `upload2-validate/upload2-confirm`(신버전) |
| **영향** | 어떤 것을 사용해야 하는지 혼란. 유지보수 비용 2배 |
| **근거** | `app/routers/nurses.py` — template-download + template2-download, 검증 로직 중복 |

**개선안**: 구버전 엔드포인트에 deprecation 경고 추가 → 프론트엔드 전환 완료 후 제거

### 2-3. 메시지 라우터 중복

| 문제 | 상세 |
|------|------|
| **현상** | `routers/messages.py`(신규, DB 기반)와 `routers/message/`(레거시, HTML 기반)가 공존 |
| **영향** | 두 시스템 중 어디로 메시지가 가는지 불명확 |
| **근거** | `app/routers/messages.py` + `app/routers/message/list.py, write.py` |

**개선안**: 프론트엔드가 `messages.py`만 사용하는지 확인 후, 레거시 `message/` 제거

## 3. 설정 UI/운영자 관점의 혼란 요소

### 3-1. 법규 vs 내규 구분이 UI에만 존재

| 문제 | 상세 |
|------|------|
| **현상** | 법규(하드 제약)와 내규(소프트 제약)가 같은 `RosterConfig` 테이블에 저장. 구분은 프론트엔드의 `ConfSection_law`/`ConfSection_hospital` 탭에만 의존 |
| **영향** | 백엔드에서 "이 설정이 법적 의무인지 운영 편의인지" 판별 불가. 법규 수정과 내규 수정의 감사 추적이 구분되지 않음 |
| **근거** | `RosterConfig` 모델에 `constraint_type` 같은 분류 필드 없음 |

**개선안 (단기)**: RosterConfig에 메타데이터 추가하지 않고, 문서와 주석으로 분류 기준 명시 (이 문서의 [02_근무표_생성규칙.md](02_근무표_생성규칙.md) 참조)

**개선안 (중기)**: 설정 필드에 `category` 태그 도입 (스키마 수준)
```python
class RosterConfigField:
    value: Any
    category: Literal["regulation", "operational", "display"]
    modified_at: datetime
```

### 3-2. 그레이드 설정 위치 분산

| 문제 | 상세 |
|------|------|
| **현상** | 간호사 등급은 `Head_nurse_management.tsx`의 GradeTable에서 설정. 등급 기반 제약은 `grade.py`로 별도 관리. 하지만 프론트에서 두 설정의 연관성이 직관적이지 않음 |
| **영향** | HN이 "등급 설정했는데 왜 반영이 안 되지?" → 제약 설정도 별도로 해야 한다는 것을 모를 수 있음 |

**개선안**: 그레이드 설정 UI에 "등급 배치 규칙 설정으로 이동" 링크/안내 추가. 또는 같은 페이지에 통합 표시.

### 3-3. 주휴 프리셉터 동기화 비가시성

| 문제 | 상세 |
|------|------|
| **현상** | 프리셉터의 주휴를 변경하면 프리셉티의 주휴가 자동 동기화되지만, UI에서 이 사실이 명시적으로 표시되지 않음 |
| **영향** | HN이 의도치 않게 여러 간호사의 주휴를 변경할 수 있음 |
| **근거** | `weekly_off_service.py:update_nurses_weekly_off_service()` — 프리셉터 변경 시 프리셉티 자동 갱신 |

**개선안**: 프론트엔드에서 프리셉터 주휴 변경 시 "프리셉티 N명의 주휴도 함께 변경됩니다" 확인 다이얼로그 추가. 백엔드 응답에 `affected_preceptees: [nurse_ids]` 포함.

## 4. 근무표 생성 엔진과의 연결점

### 4-1. 솔버 버전 관리 부재

| 문제 | 상세 |
|------|------|
| **현상** | `cp_sat_main_v3`, `cp_sat_main_v2`, `cp_sat_adaptive`, `cp_sat_basic` — 4개 솔버가 존재하지만 어떤 것이 호출되는지 런타임에 결정 |
| **영향** | 같은 설정으로 다른 솔버를 쓰면 다른 결과. 재현성 저하 |
| **근거** | `roster_create_service.py` — 여러 솔버 import |

**개선안**: `Schedule.solver_version` 필드 추가 → 어떤 솔버로 생성했는지 기록. 솔버 선택을 RosterConfig 또는 RosterRequest에 명시적으로 포함.

### 4-2. INFEASIBLE 진단 정보 부족

| 문제 | 상세 |
|------|------|
| **현상** | 솔버가 INFEASIBLE 반환 시 "어떤 제약이 원인인지" 구체적 진단 정보가 제한적 |
| **영향** | HN이 "왜 생성이 안 되는지" 모르고 시행착오 반복 |

**개선안**: INFEASIBLE 시 충돌 제약 그룹을 분석하여 반환
```json
{
  "status": "INFEASIBLE",
  "diagnosis": [
    {"constraint": "max_consecutive_work_5", "conflict_with": "insufficient_nurses_for_coverage"},
    {"recommendation": "간호사 2명 추가 또는 max_conseq_work를 6으로 완화"}
  ]
}
```
이미 `docs/INFEASIBLE_DIAGNOSTICS_FRONT_BACK_ARCHITECTURE.md`에 관련 문서가 있으므로 연동.

### 4-3. 솔버 가중치의 하드코딩

| 문제 | 상세 |
|------|------|
| **현상** | `NIGHT_DEVIATION_PENALTY`, `EXPERIENCE_SHORT_PENALTY`, 등급 penalty(160,000) 등이 코드에 상수로 하드코딩 |
| **영향** | 병원마다 다른 우선순위를 반영하려면 코드 수정 필요 |
| **근거** | `cp_sat/objective_terms.py`, `constraints/grade_constraints.py` |

**개선안 (단기)**: 현재 가중치를 문서화하여 개발자가 조정 가능하도록.  
**개선안 (중기)**: `RosterConfig`에 고급 가중치 필드 추가 (선택적, 기본값 유지).

## 5. 구조적 문제

### 5-1. Nurse 테이블 비대화

| 문제 | 상세 |
|------|------|
| **현상** | `Nurse` 테이블 35+ 컬럼: 인사정보(name, birth, phone, email) + 근무속성(experience, grade, is_night_nurse, fixed_shift) + 기능토글(enable_aide, enable_nurse_pair_preference) + 주휴(weekly_off_*) |
| **영향** | 단일 쿼리로 모든 정보를 로드. 불필요한 필드까지 전송. 컬럼 추가 시 마이그레이션 영향 범위 큼 |
| **근거** | `app/db/models.py:Nurse` — 35+ 컬럼 |

**개선안**: 논리적 분리부터 시작
1. 현재: `Nurse.*` 전체 SELECT
2. 단기: 서비스 레이어에서 필요한 필드만 명시적으로 조회 (`.options(load_only(...))`)
3. 중기: `NurseWorkProfile` (근무속성), `NursePreferences` (기능토글) 테이블 분리 검토

### 5-2. RBAC 시스템 미연결

| 문제 | 상세 |
|------|------|
| **현상** | `Permission`, `UserPermission`, `UserPermissionScope`, `PermissionAuditLog` 테이블이 완성되어 있지만, 실제 권한 검사는 `is_head_nurse`/`is_master_admin` Boolean 플래그에 의존 |
| **영향** | 세분화된 권한 관리가 불가능. "특정 그룹만 조회 가능한 관리자" 구현 불가 |
| **근거** | RBAC 라우터/서비스가 없음. 프론트엔드에서도 RBAC API 호출 없음 |

**개선안 (단계적)**:
1. **현재**: `is_head_nurse`/`is_master_admin` 유지 (작동하므로)
2. **단기**: RBAC 라우터 구현 (CRUD + 관리 UI)
3. **중기**: 기존 플래그를 RBAC으로 마이그레이션 (HN → ROSTER_CREATE 권한, ADM → ALL 스코프)
4. **장기**: 플래그 폐기, RBAC 전면 적용

### 5-3. Shift 이중 PK

| 문제 | 상세 |
|------|------|
| **현상** | `Shift` 테이블에 `shift_id`(사용자 정의 코드, PK)와 `id`(auto-increment, PK)가 공존 |
| **영향** | FK 참조 시 어디를 참조해야 하는지 혼란. `ScheduleEntry`는 `shift_id` 참조, `FixedWantedEntry`는 `shifts_table_id`(=`id`) 참조 |
| **근거** | `app/db/models.py:Shift` — 이중 PK, `ScheduleEntry.shift_id`, `FixedWantedEntry.shifts_table_id` |

**개선안 (단기)**: `id`를 안정적 참조키로 통일하는 방향으로 점진 마이그레이션. 새 코드에서는 `id` 사용.

### 5-4. JSON 컬럼 남용

| 테이블.컬럼 | 내용 | 문제 |
|-------------|------|------|
| `Group.hn_id` | HN nurse_id 배열 | FK 무결성 보장 불가, 동시 수정 race condition |
| `Nurse.is_night_nurse` | 허용 근무 코드 배열 | Boolean 이름이지만 배열, 의미 불분명 |
| `Nurse.work_shifts` | 선호 근무 코드 배열 | 인덱싱/검색 불가 |
| `ShiftManage.codes` | 허용 코드 배열 | 코드 삭제 시 일관성 수동 관리 |
| `ShiftPreference.data` | 전체 선호 JSON | 쿼리 불가, NurseShiftRequest와 이중 저장 |

**개선안 (단기)**: 필수적인 JSON(`Group.hn_id`)은 별도 조인 테이블(`group_admins`)로 전환. 나머지는 우선순위에 따라 점진 정규화.

## 7. 향후 유지보수/확장 리스크

| 리스크 | 영향도 | 발생 조건 | 대응 방안 |
|--------|--------|-----------|-----------|
| Nurse 컬럼 계속 증가 | 높음 | 새 기능마다 Nurse에 필드 추가 | 속성 분리 테이블 도입 |
| 솔버 교체/업그레이드 | 중간 | v4 솔버 개발 시 | 솔버 인터페이스 추상화 (Strategy 패턴) |
| 다국어/다기관 확장 | 높음 | 해외 병원 도입 시 | 한국 법규 하드코딩 분리, 정책 엔진 모듈화 |
| RBAC 전면 전환 | 높음 | 세분화 권한 요구 시 | 현재 플래그 → RBAC 마이그레이션 계획 수립 |
| 선호 시스템 복잡도 | 중간 | 새 선호 유형 추가 시 | 선호 엔티티 관계 리팩토링 |
