# 특정일 이후 부분 재생성 설계

> 상태: 설계안 (미구현)
> 대상: 이미 만들어진 그 달 근무표를, **특정 날짜 이후만** 다시 푼다.
> 선행 자산: `origin/docs/resignation-partial-resolve`(7/3 분기·미머지)에 퇴사자 전용
> 구현이 있으나 dev 와 한 달 벌어져 재사용하지 않는다. 아래는 현재 dev 코드 기준.

---

## 1. 문제 정의

근무표를 만든 뒤 상황이 바뀐다. 누가 퇴사하거나, 휴직이 잡히거나, 원티드가 바뀌거나,
설정을 고친다. 이때 **월 전체를 다시 만들면 이미 공지된 앞부분까지 흔들린다.**

요구:

- **재롤링 구간 밖은 손대지 않는다.** 이미 근무한 날이고 사람들이 그 표를 보고 움직였다.
- **사유를 묻지 않는다.** 퇴사든 설정 변경이든 "그 날 이후를 지금 상태로 다시 푼다"는 하나다.
- 그 달에 걸린 제약(연속근무·나이트 회복·커버리지·GRADE/Team·원티드)을 **그대로** 지킨다.
- 남은 사람의 근무 **변경을 최소화**한다.
- 원본을 덮지 않고 **새 draft** 로 쌓고, 무엇이 바뀌었는지 **diff** 로 보여준다.

### 사유 무관이라는 결정의 의미

"왜 다시 푸는가"를 API 가 알 필요가 없다. 입력 시점의 **DB 현재 상태**가 곧 사유다.

| 실제 상황 | 시스템이 하는 일 | 추가 파라미터 |
|---|---|---|
| 퇴사 | `resignation_date` 로 공급에서 빠짐 | 없음(간호사 정보에 이미 반영) |
| 휴직·파견 | 기간 테이블로 빠짐 | 없음 |
| 원티드 변경 | 바뀐 원티드를 읽어 반영 | 없음 |
| 설정 변경 | 바뀐 config 로 품 | 없음 |
| 그냥 다시 | 같은 조건으로 재최적화 | 없음 |

즉 **받는 건 기간(`from_date`~`to_date`)과 앵커 강도뿐이다.** 사전 정리(퇴사자 프리셉티
재지정 등)는 각자 자기 화면에서 이미 끝난 상태라고 전제한다 — §5.3 참조.

## 2. 핵심 구조 — 잘라 푸는 게 아니라 앞을 얼려 붙인다

날짜 범위를 잘라 별도 모델로 푸는 방식은 쓰지 않는다. **월 전체 모델을 그대로 두고**
셀 단위 하드핀으로 자유도만 제어한다.

| 셀 | 처리 |
|---|---|
| 재롤링 구간 **앞** 전부 | 원래 값으로 `fixed_cells` 핀 (동결) |
| 재롤링 구간 **뒤** 전부 | 원래 값으로 `fixed_cells` 핀 (동결) |
| 빠진 인원의 구간 내 | 공급에서 제외 (기존 `resignation_date`/기간 메커니즘) |
| 나머지 **구간 안** | 자유 변수 — 여기만 다시 푼다 |

### 2.0 재롤링 구간은 사용자가 고른다

시작일만 받고 월말까지 미는 게 아니라 **`from_date` ~ `to_date` 를 사용자가 지정**한다.
`to_date` 를 비우면 월말까지.

```
1 ────────── from ══════════ to ────────── 말일
   동결(핀)      재롤링(자유)     동결(핀)
```

구조는 시작 경계와 **완전히 같다.** 앞뒤 양쪽을 `fixed_cells` 로 핀하면 되고, 연속근무·
나이트 회복·전이 금지 같은 제약이 **같은 모델 안에서 양쪽 경계를 자동으로 인식**한다.
날짜를 잘라 별도로 풀지 않기 때문에 얻는 이점이 여기서도 그대로 작동한다.

**다만 종료 경계는 시작 경계보다 어렵다.**

| | 시작 경계 | 종료 경계 |
|---|---|---|
| 성격 | 과거는 이미 정해졌다 | **미래와도 맞춰야 한다** |
| 예 | from 직전 4연속 근무 → 구간 첫날 근무 제한 | to 마지막날 N → **다음날 원본이 D 면 ND 위반** |
| 여유 | 한쪽만 맞추면 됨 | 양쪽에 끼여 자유도가 크게 준다 |

즉 **구간이 짧을수록 infeasible 이 잘 난다.** 3~4 일짜리 구간에 나이트 회복(N 3연속 후
OFF 2회)이 걸리면 물리적으로 안 되는 경우가 흔하다. 이건 버그가 아니라 정상 실패이고,
§5.1 진단이 "구간이 좁아서"를 짚어줘야 한다.

### 2.0.1 이탈자가 있으면 `to_date` 를 뒤로 밀어야 한다

이탈자가 있는데 구간을 좁게 잡으면 **모순**이 생긴다. to_date 이후는 원본이 그대로
핀되는데, 그 원본에는 **이미 빠진 사람의 근무가 들어 있다.**

- 8/5 휴직, 구간 8/5~8/10 → 11 일 이후 원본에 그 사람 근무가 남아 그대로 핀된다.
- 결과: "없는 사람이 근무하는 표"가 뒤쪽에 남고, 그 자리는 영구 공백.

**결정: 이탈자가 있으면 `to_date` 를 월말로 강제한다.** 사용자가 짧게 잡아도 뒤로 민다.
이유를 `adjusted_reason` 에 싣는다(§2.1 의 시작 경계 당김과 같은 방식).

이탈자가 없으면(§3.5 단순 재분배) 구간을 자유롭게 좁혀도 된다.

### 2.1 ★ `from_date` 와 이탈일은 다른 경계다

둘을 뭉뚱그리면 안 된다. 역할이 다르다.

```
from_date   동결 경계 — "어디부터 다시 풀 것인가"    (사용자가 고름)
이탈일      공급 경계 — "언제부터 그 사람이 없는가"  (DB 가 정함)
```

이탈일이 `from_date` 보다 **뒤**면 문제가 없다. 8/20 퇴사·from 8/15 면 그 사람은
15~20 일까지 자유 구간에서 계속 근무하고 21 일부터 빠진다 — 기존 `active_range`
메커니즘이 이미 그렇게 처리한다. **추가 작업 없음.**

문제는 이탈일이 `from_date` 보다 **앞**설 때다. 8/5 휴직인데 from 을 8/15 로 잡으면,
동결 구간(1~14 일) 안에 **이미 빠진 사람의 5~14 일 근무가 남아 있다.** 원본은 휴직이
확정되기 전에 만들어졌기 때문이다. 이 셀을 그대로 핀하면

- 엔진은 `resignation_date`/휴직 클리핑으로 그 구간에 **변수를 아예 만들지 않는데**
  (`fallback_lex.py:214-234` 의 `join`/`leave`), 없는 변수 자리에 핀을 박는 꼴이 된다.
- 설령 통과해도 "없는 사람이 근무하는 표"가 남고, 그 사람이 메우던 자리는 공백이 된다.

**결정: 실효 시작 = min(from_date, 이탈자들의 최소 이탈일)**

즉 사용자가 고른 날보다 **앞당겨진다.** 8/5 휴직·from 8/15 면 실제로는 8/4 까지만
얼리고 5 일부터 다시 푼다. 그래야 그 사람 빈자리를 나머지가 메울 수 있다.
종료 쪽은 §2.0.1 로 월말까지 밀리므로, **이탈자가 있으면 실효 구간은 늘 [최소 이탈일,
월말]** 이 된다.

요청한 기간과 실제 기간이 달라지므로 **응답 `range` 에 실효 구간을, `requested_range`
에 요청값을 싣고 `adjusted_reason` 으로 왜 달라졌는지 알린다.** 조용히 바꾸면
사용자는 15 일까지 확정된 줄 안다.

### 2.2 이탈자를 어떻게 식별하는가 — DB 만 본다

대상자를 API 로 받지 않는다. 퇴사·휴직은 근무자 관리 화면에서 이미 처리된 상태를
전제한다(§5.3). 재생성은 그 결과를 **읽기만** 한다.

현재 코드가 인원을 빼는 경로는 넷이다.

| 사유 | 출처 | 처리 |
|---|---|---|
| 퇴사 | `nurses.resignation_date` | `_active_range_in_month` |
| 휴직·퇴사 | `nurse_assignment.reason in ("휴직","퇴사")` + `start_date` | `_clip_active_range_for_leaves` |
| 영구 전출 | 병동이동 assignment | active_range 클리핑 |
| 파견(일시) | assignment | day-block (복귀하므로 제외 안 함) |

**이탈자 = 원본 근무표에는 근무가 있는데 지금 `active_range` 가 더 짧아진 사람.**
원본 `schedule_entries` 와 현재 계산한 active_range 를 비교해서 뽑는다. 이렇게 하면
"원본 생성 이후에 새로 빠진 사람"만 정확히 잡히고, 원래부터 없던 사람은 안 걸린다.

### 왜 이 구조인가

**① 제약이 전부 재사용된다.** 커버리지·GRADE/Team 하드·연속근무·월 나이트·원티드·
공정성이 같은 모델 안에 그대로 있다. 솔버에 새 로직을 넣지 않는다.

**② 경계 연속성이 공짜로 풀린다.** `from` 직전에 누가 4일 연속 근무 중이면, 그
prefix 가 같은 모델의 고정 셀로 들어 있으므로 연속근무 제약이 경계를 정확히 인식한다.
`to` 직후도 마찬가지라 **양쪽 경계가 동시에 지켜진다.** 전월 꼬리(prev-tail)처럼
별도로 이어붙일 필요가 없다 — **이게 이 방식의 가장 큰 이점**이다. 날짜를 잘라 따로
풀면 이 경계를 손으로 맞춰야 하고, 거기서 하드락 위반이 샌다.

**③ 빠르다.** 자유 변수가 줄어 전체 생성보다 탐색 공간이 작다.

### 현재 코드의 재사용 지점 (실측)

```
fixed_cells      config_data["fixed_cells"] = [{nurse_index, day_index, shift, shift_type}]
                 소비: cp_sat_basic.py:1096  (고정 O/휴가는 off_exception 으로 확장)
공급 제외        fallback_lex.py:220-227  nu.resignation_date 이후 변수 생성 스킵
생성 진입점      generate_roster_service(req, current_user, db, config_override=...)
draft 저장       roster_create_service.py:6963  version=latest+1, status='draft'
실제 솔버        SKIP_PRIMARY=1 기본 → fallback_lex 3-stage
```

## 3. 변경 최소화 — Stage 3 앵커 한 항

`X[n,d,s]` 에서 원본 시프트를 `s*(n,d)` 라 하면 **`X[n,d,s*]` 가 그대로 "원본 유지"
지시자**다. 새 변수가 필요 없다.

자유 셀 `F = {(n,d) : from ≤ d ≤ to, n 이 남아 있는 사람}` 에 대해

```
목적항 += W_nurse · Σ_n (그 사람을 안 건드림)  +  W_cell · Σ_(n,d)∈F X[n,d,s*]
         (W_nurse ≫ W_cell)
```

사람 우선 · 칸 보조로 두는 이유: 칸만 세면 변경이 여러 명에게 흩어지고, 사람만 세면
한 명에게 몰린다. "되도록 적은 사람만, 그 안에서 총 변경 최소"가 실무 감각에 맞다.

### 어디에 넣는가 — Stage 3, 그리고 그 안에서도 맨 아래

실제 솔버는 `fallback_lex` 3-stage 서열이다.

```
전 stage 공통 하드   GRADE · team_min · fixed_cells 핀
Stage 1              커버리지 부족 최소화
Stage 2              안전/법규 위반 최소화 (연속·월나이트·전이·회복)
Stage 3              품질/선호 (원티드 · 공정성) ← 여기에 앵커를 더한다
```

앵커를 Stage 3 에 두면 **Stage 1·2 를 건드릴 수 없다.** 즉 "변경을 줄이려고 커버리지
구멍을 남기거나 ND/NE 를 새로 만드는 일"이 구조적으로 불가능하다. Stage 3 는
이전 stage 최적값을 고정한 채 풀기 때문이다.

Stage 3 **내부** 서열은 `공정성 > 앵커` 로 둔다. 앵커를 공정성 위에 두면 "통계를
깨면서까지 안 건드리기"가 된다.

### weight 조건 (지키지 않으면 앵커가 원티드를 이긴다)

```
W_cell × (자유 셀 최대 수) < 기존 Stage 3 최소 weight
```

이걸 어기면 "원본을 유지하려고 원티드를 희생"하는 해가 나온다. 초기에는 weight
바운딩으로 막고, 회귀가 나면 별도 lex 패스(원티드·공정성 고정 후 앵커만 최소화)로
승격한다.

## 3.5 이탈자가 없을 때 — 단순 재분배

이탈 리스트가 비어도(NULL) 재생성은 성립한다. 실효 구간 = 요청한 기간 그대로이고,
그 안을 **현재 조건으로 다시 푼다.** 쓰이는 상황:

- 설정(`roster_config`)을 고쳤다 — 연속근무 상한, 나이트 상한, OFF 일수 …
- 일별 필요 인원(`daily_shift`)을 고쳤다
- 원티드가 바뀌었다
- 그냥 결과가 마음에 안 들어 다시 돌리고 싶다

### ★ 여기서 앵커가 방해가 된다

변경 최소화 앵커(§3)는 "원본을 최대한 유지"하는 항이다. 이탈자가 있으면 옳지만,
**단순 재분배에서는 정반대로 작동한다** — 다시 풀었는데 원본과 거의 같은 표가 나온다.
사용자는 "재생성이 안 먹었다"고 읽는다.

게다가 솔버는 `workers>1` 이라 seed 를 고정해도 매번 다른 해가 나오는데, 앵커가
그 다양성을 눌러버린다.

**결정: 앵커 강도를 요청에서 고른다.**

| `anchor` | 동작 | 쓰는 때 |
|---|---|---|
| `strong` (기본) | 사람·칸 둘 다 억제 | 이탈자 대응 — 확정 근무표를 최대한 안 건드림 |
| `weak` | 칸만 약하게 | 설정이 조금 바뀐 재분배 |
| `off` | 앵커 없음 | 완전 재분배 — 경계 이후를 백지에서 다시 |

이탈자가 없는데 `strong` 이면 **"바뀐 게 거의 없습니다"를 응답에 명시**한다.
그래야 사용자가 `anchor` 를 낮춰 다시 시도할 수 있다.

## 3.6 기초 환경이 바뀐 것을 알려준다

재생성 결과가 원본과 다른 이유는 대개 **환경이 바뀌었기 때문**이다. 그걸 안 보여주면
사용자는 솔버가 제멋대로 굴었다고 생각한다.

### 무엇을 비교할 수 있나 (실측)

| 대상 | 원본 시점 복원 | 비교 가능성 |
|---|---|---|
| `roster_config` | **가능** — `schedules.config_id` 로 그때 쓴 설정 row 를 그대로 잡는다 | 항목별 before/after 정확히 |
| `daily_shift` | **불가** — 현재 값만 있고 스냅샷이 없다 | `updated_at > schedule.created_at` 으로 "바뀌었다"만 |
| 원티드 | 부분 가능 — 엔트리에 생성/수정 시각 | 추가·삭제·변경 건수 |
| 인원 | 가능 — §2.2 이탈자 식별과 같은 경로 | 빠진 사람 목록 |

★ **`daily_shift` 는 before 값을 알 수 없다.** 스냅샷 테이블이 없어서
"8/9 에 일별 필요 인원이 변경됨"까지만 말할 수 있고 "D 3→4" 는 못 낸다.
지어내면 안 된다 — 변경 여부와 시각만 싣고, 값을 보려면 그 화면에서 확인하라고 안내한다.
(값 비교가 꼭 필요하면 `daily_shift` 스냅샷을 근무표 생성 시점에 남기는 별도 작업이 필요하다.)

## 4. API 계약

### 4.0 2단계 플로우 — 먼저 보여주고, 그다음 실행

재생성은 되돌리기 번거로운 작업이라(새 draft 가 쌓이고 사용자가 확인해야 함)
**미리보기를 먼저 준다.**

```
GET /roster_create/partial-regenerate/preview
      ?schedule_id=...&from_date=2026-08-15&to_date=2026-08-25

200 {
  "range": {"from": "2026-08-05", "to": "2026-08-31"},   // ★ 요청과 다를 수 있다
  "requested_range": {"from": "2026-08-15", "to": "2026-08-25"},
  "adjusted_reason": "김민진 8/5 휴직 — 시작을 8/5 로 당기고 종료를 월말로 밀었습니다",
  "excluded_nurses": [ {"nurse_id","name","from","reason"} ],

  "original_config": {                       // 이 근무표를 만들 때 쓴 설정
    "config_id": 1543, "version": 12, "config_name": "8월 기준",
    "off_days": 7, "max_conseq_work": 5, "off_first": true, ...
  },
  "current_config": { "config_id": 1680, ... },
  "config_changes": [                        // 항목별 before/after
    {"key":"off_days","label":"월 휴무 일수","from":7,"to":10}
  ],
  "daily_shift_changed": {                   // 값은 못 낸다 (§3.6)
    "changed": true, "changed_at": "2026-08-09T10:22:00"
  },
  "wanted_changes": {"added":3,"removed":1,"modified":0},
  "free_days": 27,                           // 실제로 다시 풀 날 수
  "warnings": [
    "시작이 요청(8/15)보다 10일 당겨집니다 — 8/5 휴직",
    "이탈자가 있어 종료를 월말로 밉니다 (§2.0.1)"
  ]
}
```

사용자는 이 화면에서 **"무엇이 바뀌었고 어디부터 다시 풀리는지"** 를 보고 실행을 누른다.
preview 는 **DB 를 바꾸지 않는다**(read-only).

### 4.1 실행

```
POST /roster_create/partial-regenerate

{
  "schedule_id": "8375011b7181",     // 기준이 되는 원본 근무표
  "from_date": "2026-08-15",         // 이 날부터 다시 푼다 (당일 포함 — §4.2)
  "to_date": "2026-08-25",           // 생략 시 월말. 이탈자 있으면 월말로 강제(§2.0.1)
  "anchor": "strong"                 // strong | weak | off  (§3.5, 기본 strong)
}

200 {
  "schedule_id": "새 draft id",
  "version": 27,
  "range": {"from":"2026-08-05","to":"2026-08-31"},   // ★ 요청과 다를 수 있다 (§2.0.1·2.1)
  "adjusted_reason": "김민진 8/5 휴직 — 시작을 8/5 로 당기고 종료를 월말로 밀었습니다",
  "excluded_nurses": [                 // 원본 대비 새로 빠진 사람
    {"nurse_id":"...","name":"김민진","from":"2026-08-05","reason":"휴직"}
  ],
  "diff": {
    "changed_cells": 34,
    "touched_nurses": 5,
    "by_nurse": [ {"nurse_id","name","changes":[{"day","from","to"}]} ]
  },
  "warnings": [ "3/20 팀2 나이트 최소 미달", "grade-1 1명 부족" ],
  "infeasibility": { ... }           // 실패 시 기존 진단 payload 와 동일 형태
}
```

### 4.2 경계일 포함 여부

`from_date` · `to_date` **둘 다 포함**이다(닫힌 구간). "15일부터 25일까지 다시"면
15일과 25일 모두 재롤링 대상이다.

이탈일은 이와 별개로 **그 날부터 없음**을 뜻한다. "8/5 휴직"이면 5일부터 근무가 없고,
따라서 재롤링 시작은 5일이 된다(§2.1). 두 개념을 섞지 않도록 응답에서 `range` 와
`excluded_nurses[].from` 을 따로 싣는다.

경계 포함 여부를 파라미터로 열지 않는다 — 옵션으로 두면 호출자마다 다르게 이해한다.

### 4.3 실패 응답은 기존 진단과 같은 모양

부분 재생성도 infeasible 이 날 수 있다(§5.1). 이때 **일반 생성과 동일한
`infeasibility` payload** 를 쓴다. 프론트가 재생성 전용 처리를 새로 만들 필요가 없고,
방금 붙인 원인 진단(`cause_explanation` · `resolution_options`)이 그대로 재사용된다.

## 5. 리스크

### 5.1 구간을 좁게 잡으면 안 풀릴 수 있다

전체 생성이면 풀 수 있는 문제도, 앞뒤가 고정되면 해가 없을 수 있다. **양쪽이 다
핀되므로 전체 생성보다도, 시작만 고정하는 것보다도 빡빡하다.**

| 상황 | 왜 막히나 |
|---|---|
| 구간이 짧다(3~4 일) | 나이트 3연속 후 OFF 2회 같은 회복 규칙이 구간 안에 안 들어간다 |
| 종료 직후가 근무 | to 마지막날 N + 다음날 원본 D → ND 금지 위반 |
| 구간이 월말에 붙어 있다 | 자유일이 며칠 안 남아 재배치 여력이 없다 |

- 정상 실패로 취급하고 **기존 진단 경로**로 원인을 낸다.
- 다만 이 경우 원인이 "설정이 빡빡해서"가 아니라 **"구간을 좁게 잡아서"** 일 수 있다.
  진단 문구에 그 사실이 드러나야 한다 — 안 그러면 사용자가 설정을 엉뚱하게 고친다.
  → **신규 원인 1종 필요**: `partial_regenerate_infeasible`
     "8/15~8/25 만 다시 푸는 조건으로는 채울 수 없습니다. 기간을 넓히거나
      전체 재생성을 고려하세요."
  → 해결 카드도 **기간 넓히기가 1순위**다. 설정 완화를 먼저 권하면 사용자가
     확정된 월 정책을 건드리게 된다.

### 5.2 조용한 degrade — 막지 말고 보이게

인원이 빠지면 GRADE·team_min 이 **INFEASIBLE 없이 조용히 미달**된다.

- `team_min` 은 팀 활성 인원 `< min_t` 면 그 (팀,일,시프트) 제약을 **skip** 한다
  (`team_constraints.py` capacity 가드) → 미달인 채 통과.
- GRADE 는 cascade 로 하위 등급이 대체하며 페널티만 커진다 → 역시 통과.

따라서 **응답 `warnings` 에 명시**한다. 조용히 넘어가면 관리자가 모른 채 발행한다.

### 5.3 사전 정리는 이 API 밖이다

퇴사자가 프리셉터였다면 `nurse_preceptee_period` 재지정이 **먼저** 끝나 있어야 한다.
안 그러면 없는 프리셉터를 따라가는 고정이 남아 infeasible 이 된다.

이걸 이 API 안에서 처리하면 "재생성"이 "인사 정리"까지 하는 물건이 된다. **하지 않는다.**
대신 **사전 점검**으로 막는다: 재롤링 구간 안에 (a) 이미 빠진 사람을 가리키는 프리셉터
관계 (b) 빠진 사람에게 걸린 확정 원티드·고정근무 가 있으면 **400 으로 거부**하고
무엇을 정리해야 하는지 알려준다.

### 5.4 diff 는 후처리까지 끝난 표로 계산한다

고정 원티드 M-overlay 처럼 solve 뒤에 얹히는 경로가 있다. diff 를 솔버 출력 기준으로
내면 실제 표와 어긋난다. **최종 저장된 `schedule_entries` 끼리** 비교한다.

### 5.5 원본이 issued 인 경우

이미 발행된 표를 기준으로 재생성하면 새 draft 가 쌓인다. 원본 issued 는 **손대지 않는다**.
발행 교체는 기존 draft→issued 흐름을 그대로 쓴다. 이 API 는 발행하지 않는다.

| 단계 | 내용 | 산출 |
|---|---|---|
| 0 | **이탈자 식별 + 실효 경계 계산**(§2.1·2.2) | 헬퍼 1개 |

| 4 | 사전 점검(§5.3) + 400 계약 | 서비스 내 |
| 5 | diff 산출 | 서비스 내 |
| 6 | EP + 스키마 | 라우터 |
| 7 | 진단 1종 추가(§5.1) | `lagrangian.py` + 카드 |
| 8 | 프론트 — 화면 플로우·diff 표시 | 별도 |

**0·1·3·5·6 이 최소 동작 세트**다. 2(앵커)가 없어도 돌지만 변경량이 커진다.

앞(§2.1)과 뒤(§2.0.1) **양쪽 다** 해당한다.

## 7. 열린 질문

- **앵커 weight 초기값** — 자유 셀 수에 따라 바운딩해야 한다. 실측으로 정한다.
- **전체 재생성과의 UI 구분** — 같은 화면에서 어떻게 고르게 할지.
- **이탈자가 여럿이고 이탈일이 제각각일 때** — 실효 시작은 가장 이른 날 기준이라
  기간이 크게 늘 수 있다(8/3 휴직 한 명 때문에 8/25~8/27 요청이 8/3~8/31 로). 이때
  사실상 전체 재생성이 된다. → preview 의 `warnings` 로 먼저 보여주면 별도 확인
  게이트 없이 해결된다고 본다(사용자가 실행을 안 누르면 그만). **확정 필요.**
- **`anchor` 기본값** — `strong` 을 기본으로 뒀는데, 실무에서 재생성을 주로
  "이탈자 대응"으로 쓰면 맞고 "재분배"로 쓰면 `weak` 이 맞다. 어느 쪽이 잦은지에 따라
  바꾼다. (자동 판정도 가능 — 이탈자 있으면 `strong`, 없으면 `weak`. 다만 사용자가
  명시하면 그게 이긴다.)
